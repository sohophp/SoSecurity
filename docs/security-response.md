# 漏洞响应与安全发布门禁

此流程适用于 SoSecurity 核心包、可选适配包、演示和发行文档。私密报告入口、当前维护分支与公开联系方式以仓库根目录的 [SECURITY.md](../SECURITY.md) 为准；未建立的渠道和响应时限不作承诺。当前代码仍是未发布候选，不能把本流程当成已有正式安全版本或独立审查证明。

## 接收与确认

1. 在私密渠道登记报告编号、接收时间、受影响提交／版本、PHP版本、后端与部署前提。报告只保留可复现所需的最少材料；真实凭证、Session ID、TOTP秘密、恢复码和业务数据不得复制到公开Issue、日志或测试数据。
2. 用隔离环境复现并保存准确的失败结果。数据库测试仅在测试控制器创建的本地临时SQLite／无TCP MySQL中执行；不得拿生产数据库验证攻击样例。区分核心包缺陷、可选适配缺陷、宿主误配及外部依赖公告，不因WAF或应用外层拦截而忽略组件可达路径。
3. 记录攻击者所需权限、可达入口、默认配置是否受影响、数据／权限／可用性影响、已知利用条件和仍未知的前提。无法验证时标记“待确认”，不推定无影响。报告的严重度和披露安排由维护者根据证据确定，必要时先给使用方私密缓解建议。
4. 搜索同类入口和旧版本／后端，列出受影响与不受影响范围及证明方法。可能泄露的密钥、令牌或持久状态需要单独的轮换／撤销／迁移说明；补丁不能追回已经泄露的数据。

## 风险分级、处置期限与例外记录

以下为维护者内部的处置目标，适用于本项目代码及实际使用的第三方依赖，不是对外响应 SLA，也不证明已部署环境达标。维护者须为每个有效发现指定具体责任人；在没有责任人、测试条件或补丁时不能自动关闭。期限从首次获知可定位的报告或公告时间计算，评估期间不重置计时；信息不足的记录应保留未知条件并优先分诊。

| 级别 | 分诊目标 | 缓解目标 | 修复或替换目标 |
| --- | --- | --- | --- |
| 紧急：已有利用证据，或默认可达且可能导致大范围账号／秘密失陷 | 1 个自然日 | 1 个自然日，必要时停用受影响功能 | 7 个自然日 |
| 高：确认存在严重影响，需特定前提且尚无利用证据 | 3 个自然日 | 7 个自然日 | 14 个自然日 |
| 中：影响受限或需要较高权限／复杂前提 | 7 个自然日 | 14 个自然日 | 30 个自然日 |
| 低：有限加固或低影响问题 | 14 个自然日 | 30 个自然日内明确是否需要缓解 | 90 个自然日 |

依赖公告的评分用于辅助判断；须结合是否实际安装、入口可达性、配置、宿主和补偿控制记录本项目影响。尚未证明不受影响的发现不能仅凭“可选依赖”排除。修复闭环必须记录准确版本、复验结果及受影响使用方迁移状态；本地补丁不等于实际部署完成。

每条工作记录增加：首次获知时间、级别与理由、责任人、各截止日、缓解措施及验证、准确锁定依赖／提交、补丁和部署状态。超过目标必须登记阻塞。确需延期时，由维护者记录批准人、原因、剩余风险、补偿控制和明确的新到期日；不能无限期接受风险或用延期清零原始逾期。每 7 个自然日复核未结记录；新候选交付时再次列出未结、逾期及例外项。当前仓库未提供实际维护者排班、自动提醒或全使用方履约台账，故只能关闭“期限规则未定义”的文档缺口，不能关闭 ASVS 15.1.1／15.2.1 的执行验收。

## 修复与复验记录

每个发现应有一份私密工作记录，至少包含：

| 字段 | 要填写的证据 |
| --- | --- |
| 发现与边界 | 报告编号、准确入口、攻击前提、受影响提交／版本／后端、仍未知条件 |
| 复现 | 最小本地测试样例、修复前失败命令和实际结果；说明不能公开的材料保存位置 |
| 修复 | 代码差异、失败关闭策略、兼容影响、数据／密钥迁移、宿主需采取的动作 |
| 复验 | 修复后相同样例、相邻负面路径、适用PHP版本和真实测试后端的命令／退出码 |
| 独立复核 | 与实现者不同的审查者、检查范围、发现、处理及剩余风险；未安排则写“未完成” |
| 披露 | 私密通知、公告草稿、公开时间与实际发布／部署证据；未发布则写“未执行” |

当复现会破坏数据、触发外部服务或需要真实下游接入时，先在隔离测试数据上完成可做的证据，剩余验证明确交给相应环境负责人。失败的初轮与修正版结果都保留，不能用后一次成功覆盖已知缺口。安全修复变更同步更新[威胁模型](threat-model.md)、使用指南、[变更日志](../CHANGELOG.md)和适用测试。

## 候选发布门禁

针对**同一准确候选提交**核对以下证据，任一项未知就保留未完成状态：

1. 确定本次稳定范围、受影响版本、配置／API兼容和升级／回滚步骤；[安全精修跟踪](security-refinement.md)中的适用项有实现、指南和相应验收。隔离候选代码不能作为已发行能力。
2. 冻结准确候选提交后，在PHP7.2—8.5九版各运行一次完整门禁；覆盖所声明的SQLite、私有MySQL、Redis、HTTP／TLS、并发与故障路径。开发中的局部修复先复测受影响项，不以重复九版整轮代替问题定位；候选代码改变后重新登记候选并复验。缺扩展而跳过的必需测试不得记为通过，真实浏览器或下游验收单独列出。
3. 核心包和可选包分别做全新Composer消费者安装、严格清单校验与归档内容检查；归档包含准确源码、说明和许可，不包含测试秘密或开发产物。审计每个实际锁定的第三方依赖集；根包没有已安装第三方包时记为“不适用”，不能把审计命令无对象退出误写为绿色。
4. 对照CI中同一提交的实际运行结果，而不是本地配置文件或历史绿色记录；失败、跳过和未触发项逐项说明。静态检查、发布包校验及已知高风险默认值复核都需留证据。
5. 独立审查者复核威胁边界、公开API、敏感数据生命周期、危险状态恢复和修复前反例；维护者逐项处置发现。作者自检、自动扫描及未安排审查不能代替此项。
6. 准备私密使用方通知与公开公告，写明影响、修复版本、升级操作、剩余风险及部署验证范围。提交、推送、打标签、发布包、登记包仓库和生产部署各按用户的明确授权执行，不因门禁通过自动触发。

这份清单描述发布所需证据，不宣称当前候选已通过。具体当前状态见[发行候选工作单](release-readiness.md)及[验证记录](verification.md)。
