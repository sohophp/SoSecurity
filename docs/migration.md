# 旧 PHP 网站分步迁移

R6.3可信设备风险决策为可选增量：未配置`remember.risk_guard`时，原记住登录恢复行为保持。配置后须注入返回`Auth\DeviceRiskDecision`的服务，并处理新增`step_up`和`blocked`状态；两者均不得建立登录态，都会在同一事务中撤销设备授权及关联会话；宿主均须清除本地Cookie。`step_up`引导完整重新认证，误判后也必须由用户主动签发新授权。原因码仅用于服务端审计；完整信号来源与误判流程见[记住登录指南](remembered-login.md#可选可信设备风险决策)。

## 签名链接与请求／响应对象导出修复

`Link\IssuedLink`、`Webhook\Request`及`Idempotency\Request`／`Response`过去可由`var_export()`读出完整凭据URL、原始请求或业务正文。当前版本将敏感值保存在闭包内，保留公开getter返回的原始字节，并拒绝旧对象反序列化。部署时从当前权限源、HTTP请求或可信业务结果重新构造；若曾记录对象导出，按实际访问范围清查凭据URL、签名头和业务数据，必要时撤销链接或处置已暴露信息。

## 认证结果与密码记录的对象导出修复

`Auth\PasswordRecord`的密码哈希和`Auth\LoginResult`的MFA挑战值此前可由`var_export()`读取。当前版本将两者保存在闭包内，保留`hash()`、`identity()`和`challenge()`的返回值，并拒绝旧对象反序列化。部署时从可信账号存储和当前认证状态重建对象；若曾将对象导出写入日志或文件，应清查实际暴露范围，按认证事件与密钥管理流程处置。不要把对象转储当作会话或账号记录。

## Webhook密钥快照导出修复

`Webhook\KeySet`原先将完整原始密钥放在普通私有数组中，`var_export()`仍可读取，即使调试输出已遮盖。当前版本改为闭包保存密钥，保留`verify()`和`fromEncoded()`行为，并拒绝反序列化旧对象。若宿主曾缓存序列化的`KeySet`，需在部署时从可信配置重建并重启长驻进程；若曾把对象导出写入日志或文件，应按实际暴露范围检查并决定是否轮换密钥。此修复不清除既有转储。

## 签名与验证码密钥对象导出

`Api\SigningKey`及`Captcha\Turnstile`／`Recaptcha`／`HCaptcha`不再支持序列化保存或恢复。此前直接`print_r`／`var_dump`验证码实例，或`var_export`／`serialize`上述对象及包含它们的服务对象，可能把服务端密钥写入日志、缓存或调试转储。新代码把私有密钥保存在闭包内，常见导出不展开原始字节，反序列化旧对象明确拒绝；`SigningKey::secret()`、API签名和三个服务端验证码请求仍按原接口工作。

使用方应只保存不含秘密的标识，并在每次工作进程初始化时从可信服务端配置重建这些对象；部署时重启长驻进程。按实际日志／缓存暴露范围清查历史转储，并由密钥管理者判断是否需要轮换。该修复不能删除已泄露内容，也不隔离反射或同进程内存读取。

同类原始属性暴露也已在`Api\Credential`／`IssuedCredential`、`Auth\SessionCredential`／`RememberCredential`、`Concurrency\Lease`、`Operation\Confirmation`／`Grant`、`Webhook\ProcessingClaim`和`Download\SessionAccess`修复。公开`token()`结果保持原字节；常见对象导出不再展开完整令牌，序列化或恢复旧对象明确拒绝。宿主应保存经设计允许的**单个受保护令牌字符串**或当前授权来源，不保存整个服务／结果对象；已写入日志的旧令牌须按用途撤销、过期或轮换。`SessionAccess`的请求绑定对象每次请求重建。修复不改变已签发凭据本身或服务器账本格式。


可选ZIP检查没有数据库结构、持久状态或自动迁移。需要接收归档的宿主先部署`ext-zip`，完成上传授权和私有暂存，再显式调用[归档只读检查](archive-inspection.md)；缺扩展时明确拒绝该入口。检查返回后不要用同一路径自行解压并声称已受保护：提取流程、源文件替换与目录内链接竞态需要独立设计和验收。普通上传与现有隔离流程不会自动改变。

`Http\Cookie::header()`现在拒绝URL编码后名称、等号和值超过4096字节的Cookie，并在编码前拒绝原始超限输入。若宿主原先依赖超长Cookie，应迁移到服务端状态或使用有界的随机引用值；不要截断已签名或已加密的令牌。这项变更不修改Cookie名称、属性默认值或短值的编码方式。

原生 Outbox 可选独立权限库的显式 DDL、当前来源核对、停止旧进程和私有配置步骤见[独立权限源迁移](outbox-authority.md)。该功能需要 ext-sqlite3，不自动导入业务备份内的历史权限；源与业务共同回退的权威基线责任保留。

当前未发布候选不自动接管路由、业务数据库、认证／授权、Session生命周期或文件管理器。认证、授权及高风险操作组件需宿主显式接入；先在指定测试环境验证，再选择获授权的业务入口迁移。原有检查继续保留到替代路径真正验证通过；不要同时删除所有旧代码。

## 1. 接入前盘点

私有安全表现在严格拒绝入站／出站外键，包括 Outbox、幂等、Webhook 接收／处理及 MySqlStore；关闭执行开关仍拒绝，缓存的 MySqlStore 实例每次自有事务也重新检查。规范 DDL、公开接口和状态格式未因这项检查改变。已有非规范关系须停用相关工作进程、审阅完整依赖并执行显式迁移，不能自动删约束或清空账本；账号看不到的跨库关系仍须部署者审核。详见[SQL 依赖边界](sql-transactions.md#私有安全表的依赖边界)。

事务发件箱为显式启用的候选接口，原有项目无需添加配置。需要接入时，由宿主迁移安装专用结构、使用独立封存密钥与外部epoch，并用受控管理程序初始化作用域／生产者；不能在HTTP请求或诊断中自动补表或重建缺失根。业务更新与enqueue必须使用同一PDO和宿主显式事务，错误中止整个业务单元；工作端另外领取，发送与接收去重仍须单独接入验收，见[Outbox](outbox.md)。

原生Outbox接收候选现要求业务根、独立持久检查点、外部epoch和预建锁文件；由迁移安装新增结构及私有配置，再显式初始化空接收库。非空未封存旧候选库不能自动采用，须先进行权威业务对账与迁移。停机、备份、一个已知转换的恢复及代际旋转顺序见[接收恢复指南](outbox-recovery.md)，不能把独立检查点与业务库一同回退或删除历史重新初始化。

Outbox显式超期处置会首次把对应命名空间根及处置记录的封存format推进为2，并新增resolved终态；SDK DDL及其他行字段不变，新代码继续读取未处置的格式1命名空间。启用前停止旧生产／发送／管理进程，部署支持格式2的代码与宿主审计guard后再处置；旧代码严格拒绝格式2，不能仅回退代码或手改format。原生证据／取消栅栏另有示例数据库增量 DDL、独立签名种子／公钥、管理角色及显式审计初始化；首次取消也推进接收业务根为格式 2，见[超期对账](outbox-reconciliation.md)。

原生发送端另可显式启用[审计归档](outbox-audit-archive.md)：已有库先执行归档增量 DDL，并从权威当前审计根独立保留升级摘要，再配置 `resolution_archive` 并通过显式命令推进发送审计根为格式 2。它不修改 SDK 队列 DDL，也不能与接收业务根版本混淆；关闭开关或旧代码均不能继续读取已升级的归档审计。

列出登录、注册、找回密码、后台表单、AJAX和上传入口，标记认证凭证是Cookie还是Bearer。查清Session驱动是否加锁，代理是否正确重写X-Forwarded-For，已有框架是否自带CSRF。备份配置和原有实现，不备份明文密码到日志。

Composer公开包尚未发布，当前使用README中的路径仓库安装。指定测试站点唯一namespace，私有目录必须在Web根之外、0700且应用拥有；跨主机共享状态显式配置Redis或MySQL，禁止SessionStore做跨会话登录限流。MySQL共享状态适配已经实现，见[MySQL指南](mysql.md)；安装状态表和宿主业务表迁移仍须显式管理，不自动修改业务结构。

## 2. 先加请求预算

保留原密码验证函数，在它前面调用 `RateLimiter::consume`。账号规范化使用原有登录规则，避免不同大小写/别名绕过预算。用组合IP+账号桶保护密码计算，用阈值较宽的IP桶控制总体请求；不要默认锁死账号或共享IP。

第一阶段可以单独记录预算结果来评估阈值，但原有防护必须保持；真正启用时 denied 立即结束业务，临时拒绝返回429/Retry-After，存储故障返回503。验证码生成/刷新也限流。成功登录不要默认清空宽松IP总量桶。

## 3. 替换一个验证码入口

替换生成端及服务端验证端，保留相同业务路由。绑定Session中的随机值和具体scope，表单提交 challenge.id 与用户答案。刷新先revoke；不要把答案、摘要、Session ID交给前端。AJAX和传统表单使用相同后端检查，任何依赖异常都拒绝业务。

多标签页默认保留4个挑战；并存容量可配置。先验证正常/错误/过期/重放/并发提交，再移除旧答案存储键。数学和基础图片不证明能抵抗自动识别；高风险入口可启用Turnstile并保持现有业务限流。

## 4. 加CSRF

已有Symfony等框架提供正确CSRF时优先保留；没有时使用CsrfTokens。按scope给每个表单发令牌，放隐藏字段或AJAX请求头，验证后才执行状态变更。选择足够的并存容量和TTL，验证多标签页/长时间打开页面后刷新流程。

不要使用GET写数据；不要给所有路径做通配符豁免。兼容老前端可先给页面加隐藏字段，再在后端强制检查；旧防护不能在改前端时一并撤掉。无Cookie自动认证的Bearer API需根据实际机制分析，不机械套表单规则。

## 5. 密码渐进升级

复用原有用户查询（参数化SQL）。针对准确旧格式注入legacyVerifier，仅验证成功时生成现代哈希，再按原哈希CAS更新：

```php
$result = $hasher->verifyAndUpgrade($submittedPassword, $row['password_hash'], $legacyVerifier);
if (!$result->valid) { /* 返回统一登录失败 */ return; }
if ($result->replacementHash !== null) {
    $statement = $pdo->prepare('UPDATE users SET password_hash = :new WHERE id = :id AND password_hash = :old');
    $statement->execute(['new' => $result->replacementHash, 'id' => $row['id'], 'old' => $row['password_hash']]);
    // 若未更新到1行，重新读取确认账号状态；可能发生密码重置，不能按旧凭证继续登录。
    if ($statement->rowCount() !== 1) { /* 请求重新认证 */ return; }
}
```

表名/字段仅示例，不能未经审核在宿主执行。根据现有哈希长度审核列容量（通常至少255字符）。未知旧格式、不可验证哈希、超bcrypt字节上限的旧密码不能安全自动迁移；采用支持的Argon2id或受控重置。禁止把哈希改成“先MD5再bcrypt”规避长度限制。

## 6. 会话与Cookie

把configure放在宿主session_start之前；登录/权限提升确认成功之后且写认证状态之前rotate；敏感页面调用touch，false立即取消宿主认证。PHP7.2在start/rotate后显式发送cookieHeader，同名同路径的最后一个Cookie头携带SameSite属性。生产只用HTTPS和Secure。

不自动处理宿主退出登录字段，先确认现有path/domain、并行请求行为、自定义Session驱动的strict_mode支持。更新Session ID时旧并发请求可能失败，验证表单/AJAX重试体验。

## 7. 输出和响应头

保留Twig自动转义；普通PHP仅替换对应HTML/引用属性输出，不对整个输入先“清洗”再宣称没有XSS。JS只以JSON数据方式注入，不生成用户可控代码。CSP先Report-Only，收集违规后检查第三方资源；HSTS待HTTPS和恢复流程验证后显式启用。

现有CKFinder／上传系统先保留，逐入口接入[上传校验](upload.md)与出站请求约束后再核验替换范围。组件已经实现内容／资源预算及出站请求防护，但安装本库不代表旧入口已调用，也不替代文件管理器的对象授权或真实扫描服务验收。

## 观察与回滚

观察只记录固定事件代码、响应状态、Retry-After和假名化主体，不能记录密码、验证码答案、Cookie、令牌或完整请求。明确保护开关和异常响应；测试误封率与共享IP正常用户。

回滚时先恢复原有可靠防护，再停用新调用；若旧实现已知不安全，回滚不能意味着匿名放行，可暂时关闭该敏感入口。CSRF/验证码切换后的旧表单可能需刷新，通知用户并保留正常错误响应。不要通过清空所有Redis/Session/文件数据来恢复访问，这会删除封禁及单次消费状态。

## 本地完整示例

[legacy-login.php](../examples/legacy-login.php) 是可运行的原生PHP示例，需要：

- `SOSECURITY_EXAMPLE_STORE`：预创建的0700私有目录；
- `SOSECURITY_EXAMPLE_USER`：测试账号；
- `SOSECURITY_EXAMPLE_PASSWORD_HASH`：原生password_hash生成的哈希，不是明文密码；
- `SOSECURITY_EXAMPLE_HTTPS`：默认Secure，仅隔离本地HTTP设为0。

不要将示例直接作为生产认证平台。`python3 tests/test_http.py php72` 会创建独立环境并验证真实HTTP、Cookie和登录流程，不连接旧网站数据库。真实站点的授权和业务数据验收仍需在宿主进行。

## 审计日志对象的调试与持久化

AuditLogger的print_r／var_dump输出只显示脱敏标志，回调捕获的秘密和审计假名密钥均不展开；默认JSON仍不导出私有字段。serialize()现在明确抛出ConfigurationException，不再支持把服务对象连同私有材料写入缓存或传输。

需要跨请求使用时，保留不含秘密的配置标识，并在可信初始化流程中重新注入sink和私有材料。既有事件字段及主体HMAC计算不变；服务对象缓存须迁移。历史调试／序列化输出按实际暴露范围检查和处置，这项修复不会删除历史转储或自动轮换在用密钥。任意反射、进程内存及宿主自行导出秘密仍由调用方控制。

## 私有密钥与审计对象导出

Cipher／HmacKeys／AuditLogger 新代码以闭包保存私有密钥或审计回调，常见对象导出不会自动展开这些值，签名／加密格式及日志字段保持。对象本就不支持序列化恢复；更新后由可信配置重建，长驻工作进程需要重新加载代码。不要将旧对象属性数组当作持久配置或恢复格式；重建状态不符合内部类型时拒绝处理。此保护覆盖正常对象的受控调试／JSON／var_export，不提供反射或同进程内存隔离，其他敏感对象仍需分别复核。

## 上传快照与保存结果的持久化迁移

`Upload\Candidate` 的正文与 `Upload\StoredFile` 的私有完整路径不再出现在普通对象导出中，serialize／unserialize明确拒绝。显式 `contents()`／`path()`、字节数／摘要／元数据返回值保持；服务器端扫描及已授权文件管理接入继续使用这些方法。

曾将这两类对象放入Session、缓存或队列的代码，应改为保存可信资源标识与允许的元数据，并在当前授权下重新读取及验证来源。长驻进程需加载新代码；旧序列化对象不能作为可信恢复材料。新代码不会删除历史日志或缓存中的旧正文／路径转储，历史处置按实际数据暴露范围处理。
