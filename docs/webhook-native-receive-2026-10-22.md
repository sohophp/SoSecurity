# Webhook 原生接收准入

> 后续：原生处理入口已补齐并完成专项验证，见[处理专项](webhook-native-processing-2026-10-22.md)。本记录保留原阶段的源码与验证范围，不代替后续结果。

本批继续非暂缓功能：原先声明与工厂绑定仍要求手工进入边界，普通无效请求也无法在写入 pending 前完成完整接收判断。现已为配置 StateWebhookConnection 的 SqlInbox 接通原生接收。这里只覆盖接收；SqlProcessor 原生处理准入、其他计划余项及完整稳定版验收仍未完成，goal 保持 active。

## 实现与边界

- 原生 accept 在见证锁内先验签、映射、检查当前请求与业务关联权限、期限、已存在消息冲突和声明行容量。拒绝时见证记录保持不变；满容量时允许匹配的重复消息，拒绝新消息。观察查询使用只读 SqlTransaction，读取正文长度而非完整正文。
- 完整来源再次核对后创建限定 `webhook.receive` 的意图，绑定端点、消息描述、正文摘要、来源密钥、状态摘要及声明。摘要记录不含原始事件标识或正文。效果阶段保留原 SQL 接收事务、重验签、当前权限和回滚保护，消息映射必须与准入一致。
- 全阶段共享接收 I/O 预算和单调的业务时间检查。声明匹配确切固定 KeySet 提供器、端点和时钟。原生接收拒绝嵌套，异常后清除进程内准入标记；不会清除持久待处理记录。
- 准入回调属于可信宿主，只允许只读、可重复的映射和权限查询；完整来源必须覆盖其可变依赖。本实现不能强制任意宿主代码只读，也不提供外部权限系统原子性。
- 映射在效果阶段变化时 SQL 保持不变、见证保留 pending 并返回 account.completion_unknown。测试只证明拒绝与保留状态，未实现、执行或续办未知结果，没有恢复激活或安全代际交接。

## 旧证据更正与兼容

旧 `webhook-request-authority.php` 的 commit 模式在第二轮验签撤权，实际上尚未开始事务，不能支持旧报告的“INSERT后回滚”。本次移至第三轮验签，明确断言 INSERT 已执行、最终零行且事务退出，九版及两端MySQL通过；原日志保留，旧报告加注更正。普通成功接收通常六次请求保护调用，原生接收通常八次，旧文“四次”计数不正确。此为原生准入初轮代码的次数；下述后续完成阶段修复后，普通路径通常十次、原生路径通常十二次。

公开类型保持270；实际反射发现 StateOperation 也属于现有候选，不能按内部实现忽略其变化。已审查新增方法及 SqlInbox 最末可选参数，断言全部既有类型／成员保持，只有该构造器新增兼容参数。保留 `api-before.json`、独立提案、成员差异和审查结果，随后才更新候选。

普通未配置状态声明的接收用法保持。配置声明的 accept 现在直接调用，不能再套 boundary.run；处理入口仍要求显式活动边界。原始PDO和绑定前构造的服务仍拒绝边界外访问。暂缓项、在线提供器、旧ApiKeys、维护等余项、历史PHP7.2维护超时及外部验收保持开放。没有提交、推送、部署、生产访问或撤销既有改动。

## 同批继续修复：完成阶段撤权

继续检查发现接收在最后正文一致性SQL读取、COMMIT或恢复连接超时参数期间撤权，仍可能返回成功。`completion-authority-before.log` 保存修复前真实失败 `Withdrawn completion authority accepted: request/final-read`。

现在在提交前、完成清理后重新验签并检查业务关联，仍使用同一预算与时钟边界。提交前拒绝回滚；提交后拒绝不伪造回滚，已提交接收行保留，不返回成功回执。原生入口保持 pending 和 account.completion_unknown；测试不续办、不重置、不恢复未知结果。

新增 `tests/webhook-completion-authority.php` 覆盖请求权限／关联权限／密钥三类撤销与最后SQL读取／提交／清理三个阶段，共36断言；原生 `completion-revoke` 模式79断言检查提交后留存一行、无活动事务、见证pending。最终代码的复验以 `final-matrix.json`、`completion-revoke.json`、`mysql-completion.log`、`static-completion.log`、`final-consumer/archive.json` 为准；前述初轮日志保留为历史快照，不能替代最终代码验证。补查的原因是新发现且已修改的完成阶段缺陷，不是重复追求绿色结果。

最终结果：`final-matrix.json` 63条中62条通过、1条失败（PHP7.2共享账号完整快照的 sql.timeout）；`completion-revoke.json` 九版全部通过。私有MySQL两端16条及最终全新归档消费者18条全部通过，静态分析和最终两端270类型API检查通过。失败日志 `final-shared-72.log` 保留；随后原运行时和现有原生单调时钟运行时各一次同源码诊断均通过，耗时约2.31秒／2.16秒（`shared72-diagnostic.json`）。这不能确定超时原因，更不能证明修复，不称最终候选全绿；没有改预算或默认拒绝。最终摘要为 `final-results.json`。
