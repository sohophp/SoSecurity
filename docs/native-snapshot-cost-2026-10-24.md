# 默认签发的快照与账本成本定位（2026-10-24）

在凭据冷路径修复后，对新的私有MySQL环境分三次进行不同层次的诊断，逐层缩小未解释的耗时。每次使用实际PDO、SystemClock和原3000ms预算，只到首次符合签发条件的调用，失败后读取状态；没有续办未知回执、执行账号恢复或安全代际交接。SDK源码保持，仅预加载诊断副本添加计时和不含参数的调用栈，不记录SQL、密钥、令牌或主体数据。所有副本及日志排除于发行归档。三个结果与自身清理均经[汇总](native-snapshot-cost-evidence-2026-10-24/summary.json)核对。

第一次仅记录Composite各子来源观察，结果约3.0026秒失败、pending；64次观察均完成，累计约0.6253秒。16次SQL观察约0.6122秒，16次文件观察约0.0090秒，其他为栅栏及Webhook来源。因此完整SQL快照是成本之一，但该观察未覆盖整个签发窗口。

第二次增加账本与事务方法的聚合计时，结果约3.0034秒失败、pending。`verifyLedgerSchema`调用269次、累计包容耗时约1.459秒，`checkedRoot`调用243次、约1.571秒；`metadataRows`1145次、`query`887次。`history`认证逻辑本身累计约0.0039秒。上述方法会嵌套，时间不得相加，方法调用数也不等于服务器SQL语句总数。原始数据在[方法成本](native-sql-cost-evidence-2026-10-24/costs.json)。

第三次以账本调用栈分类，结果约3.0038秒失败、pending。242次 `checkedRoot` 中，152次来自 `FactorWorkerAuthority::assertCurrent` 经 `SqlTransaction::readIn` 的当前工作进程证明；40次来自其普通请求检查；其余25次 `readCheckpoint` 与25次 `readIfCheckpoint` 来自 `FactorRegistry::snapshot`／`bindingUnfenced`。见[计数及调用栈](native-ledger-callers-evidence-2026-10-24/costs.json)。本批三个异常栈均在凭据内部写入后的 `CredentialRegistry::issued` → `actor` → 第二次会话验证阶段失败；不能把先前系统调用诊断的异常阶段套用于这些新运行。

当前证据将主要调查方向收窄至传统身份读取的重复MFA目录／当前工作进程校验。当前源码的 `actor` 在已有原生准入时仍调用普通会话验证与身份加载，进一步触发目录和工作进程读取；未来若改为捕获式读取，必须保留当前工作进程有效性、真实目录映射、提供器／回调权限变化、事务边界及签发后最终拒绝。仅用新来源摘要替代旧摘要，或缓存准入身份后直接返回，都不足以证明等价性。本批没有实施这种替换，也没有改变工作进程登记或交接。

这些运行均是带计时副本的诊断，不计入普通专项或性能验收，不覆盖此前失败。冷路径专项仍为38配置37通过／1失败，消费者8步7通过；默认原生首次签发缺口未关闭。最终非暂缓候选仍未完成，goal保持active。
