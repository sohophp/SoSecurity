## 一、项目概述

**项目名称：** SoSecurity
**GitHub 仓库：** [https://github.com/sohophp/SoSecurity](https://github.com/sohophp/SoSecurity)
**Composer 包名：** `sohophp/sosecurity`
**支持 PHP 版本：** PHP 7.2 ～ PHP 8.5
**项目定位：** 开源、独立、模块化、框架无关的 PHP Web 安全加固组件库。

### 项目目标

开发一套完整、可靠、易于集成的 PHP 安全组件库，为现有 PHP 网站及新项目提供统一的安全防护能力。

项目主要用于改善已有 PHP 网站的安全性，逐步替换历史遗留的验证码、CSRF、登录防护、密码处理、文件上传等安全代码。

需要同时适用于新项目，提供清晰、现代、可维护的安全 API。

SoSecurity 不是一个完整的 PHP 框架，不负责替代现有应用的路由、数据库、认证系统、权限系统或业务逻辑。

项目应能够独立安装、按需启用功能，不强制依赖 Symfony、Laravel 或其他 PHP 框架。

### 核心原则

1. **安全优先：** 遵循成熟的安全标准，优先采用经过验证的安全机制。
2. **完全开源：** 项目公开所有源代码，安全性不依赖隐藏实现、代码混淆或私有算法。
3. **向下兼容：** 支持 PHP 7.2～8.5，允许老项目继续使用现有 PHP 环境。
4. **低侵入性：** 尽可能少地修改旧项目已有的业务代码。
5. **模块化：** 所有安全能力可以根据项目需求独立使用。
6. **避免重复：** 已有模块能够承担的功能，不单独创建重复模块。
7. **可配置：** 防护规则、阈值、有效期、存储方式等可以配置。
8. **高性能：** 尽量降低对正常请求性能的影响。
9. **可扩展：** 允许用户替换存储、验证机制和防护策略。
10. **长期维护：** 以稳定、简洁、可测试的设计为目标，避免不必要的抽象和过度工程化。

## 二、功能需求

以下是期望具备的安全能力，不代表必须将每项功能设计成独立模块。

Codex 应根据实际职责、依赖关系、复杂度和维护成本，自主决定如何合理组织功能。

### 1. CAPTCHA — 验证码

提供适用于登录、注册、找回密码、评论、联系表单等场景的验证码功能。

期望支持：

- 图片验证码，可配置字符长度、字符集、图片尺寸、字体及干扰效果。
- 算术验证码。
- 可扩展的第三方验证码，例如 Cloudflare Turnstile。
- 验证码有效期、刷新、错误次数限制。
- 验证成功后失效，防止重复使用。
- 验证码与具体业务场景绑定。
- 支持 Session 及其他适当的存储方式。
- 支持传统 HTML 表单和 AJAX 请求。
- 支持与请求限流、登录防护联动。
- 在合理场景下支持按风险决定是否需要验证码。

验证码不得仅依赖前端验证。

优先选择实用、安全、易于集成的方案，不追求复杂但缺乏实际安全价值的验证码形式。

### 2. CSRF — 跨站请求伪造防护

提供统一、可靠的 CSRF 防护能力。

期望支持：

- CSRF Token 的生成和验证。
- Token 有效期和作用域管理。
- 传统 HTML 表单与 AJAX 请求。
- Session 环境与适当的无状态验证方案。
- 多标签页、长时间打开的表单等常见使用场景。
- Token 防伪造、跨场景滥用及必要的重放保护。
- 与现有 Session 系统兼容。
- 适合 Twig 等模板系统的便捷集成方式。
- 可配置的路径或请求类型豁免规则。

应根据不同认证方式判断是否需要 CSRF 防护，不对所有 API 请求机械地使用相同策略。

### 3. Rate Limiting — 请求限流与自动封禁

提供统一的请求频率控制、防暴力破解和自动封禁能力。

期望支持：

- 按客户端 IP 限制请求频率。
- 按账号、IP+账号、路由、行为类型或自定义标识限流。
- 登录密码猜测、验证码猜测等暴力破解防护。
- 可配置的失败次数和统计时间窗口。
- 达到阈值后自动封禁。
- 支持临时封禁、阶梯封禁和手动永久封禁。
- 封禁到期自动恢复。
- IP 黑名单、白名单及 CIDR 规则。
- 不同业务场景使用不同限制策略。
- 封禁记录查询、手动解除和管理。
- 合理的错误响应和 Retry-After 信息。
- 支持多站点、多进程及并发请求。
- 避免共享 IP 用户被大面积误封。
- 避免攻击者利用账号锁定机制恶意阻止正常用户登录。
- 支持安全事件触发相应防护策略。

要求在正常流量、恶意请求和并发环境下都具有可靠的行为。

自动封禁属于 PHP 应用层防护，不需要模拟系统防火墙，也不应宣称能解决网络层 DDoS 攻击。

### 4. Session Security — 会话安全

改善 PHP 原生 Session 及已有应用 Session 的安全性。

期望支持：

- Session 固定攻击防护。
- 登录、权限提升等关键操作后的 Session ID 更新。
- Session 超时和空闲过期策略。
- Session Cookie 的 Secure、HttpOnly、SameSite 等安全属性。
- Session 注销和失效管理。
- 与现有 PHP Session 系统兼容。
- 合理防范会话劫持和会话重用风险。

不能强制接管或破坏宿主项目已有的 Session 生命周期。

### 5. Password Security — 密码安全

提供安全的密码处理辅助能力。

期望支持：

- 使用现代、安全的密码哈希算法。
- 密码哈希验证。
- 哈希参数升级及重新哈希。
- 旧项目遗留密码哈希的安全迁移。
- 密码强度与基本安全策略检查。
- 根据需要检查已知泄露密码。
- 密码重置相关的一次性令牌安全机制。

不得自行设计密码哈希或加密算法。

旧密码系统迁移时，应尽可能保证用户无需集中重置所有密码，同时明确无法安全自动迁移的情况。

### 6. HTTP Security — HTTP 安全防护

提供常见 HTTP 安全策略的配置和应用能力。

期望支持：

- Content Security Policy（CSP）。
- CSP Report-Only。
- HTTP Strict Transport Security（HSTS）。
- X-Content-Type-Options。
- Referrer-Policy。
- Permissions-Policy。
- 点击劫持防护。
- 安全 Cookie 属性管理。
- CORS 策略管理。
- 开放重定向防护。
- 可信代理与真实客户端 IP 解析。

应兼容 Apache、Nginx、PHP-FPM 以及存在反向代理的部署环境。

安全配置不得轻易破坏现有网站的 JavaScript、静态资源、第三方服务或跨域请求。

对于可能引起兼容性问题的安全策略，应提供合理的迁移方案。

### 7. XSS — 跨站脚本攻击防护

为旧 PHP 项目提供安全、易用的输出处理能力。

期望支持：

- HTML 文本上下文的安全输出。
- HTML 属性上下文的安全输出。
- JavaScript、URL 等不同上下文的安全处理指导或辅助功能。
- 与 Twig 等模板系统的转义机制兼容。
- 在确实需要用户输入 HTML 的场景中，支持经过审查的 HTML 清理方案。

必须区分输入验证、输出编码和 HTML 清理，不采用简单删除危险字符串的方式宣称能够全面防止 XSS。

### 8. Input Validation — 输入验证

提供常用输入验证和规范化能力。

期望支持：

- 字符串、数字、布尔值等数据类型验证。
- 长度、范围、格式、枚举值验证。
- 邮箱、URL、IP 地址等常见格式验证。
- 数组及嵌套数据验证。
- 可扩展的自定义验证规则。
- 清晰、可本地化的验证错误信息。
- 合理处理 Unicode、编码及边界情况。

避免与宿主项目已有验证框架发生冲突。

### 9. File Upload Security — 文件上传安全

为旧项目中常见的不安全上传代码提供可靠替代方案。

期望支持：

- 文件大小和类型限制。
- 安全文件名生成。
- MIME 与文件内容类型检查。
- 文件扩展名白名单。
- 防止路径穿越。
- 防止上传可执行恶意文件。
- 安全存储位置控制。
- 上传目录与 Web 可访问目录隔离。
- 对图片、文档等常见上传类型提供合理安全策略。
- 根据实际需要支持外部恶意文件扫描服务。

如果项目已有 CKFinder 或其他文件管理器，应能够通过适配方式复用必要的安全校验，而不是要求替换整个文件管理系统。

### 10. URL / SSRF Security — URL 与服务端请求安全

为应用中访问外部 URL、下载远程资源和处理跳转的场景提供安全辅助能力。

期望支持：

- URL 格式和协议校验。
- 阻止不安全的协议。
- 限制访问内部网络、环回地址及敏感目标。
- 处理 DNS 解析、重定向及地址变化风险。
- URL 主机白名单。
- 安全跳转目标验证。
- 防止开放重定向。

必须明确适用范围，不提供虚假的“验证 URL 一次即可永久安全”保证。

### 11. API Security — API 安全

为采用 HTTP API 的 PHP 项目提供可复用的请求安全能力。

期望支持：

- API 请求限流。
- API Key 的安全验证与管理辅助。
- HMAC 请求签名。
- 时间戳、Nonce 和重放攻击防护。
- 统一的安全错误响应。
- 与 Cookie、Bearer Token 等不同认证方式兼容。

不要求开发完整 OAuth 服务或身份认证平台，优先提供现有项目可以复用的安全组件。

### 12. Security Audit — 安全审计

提供统一的安全事件记录及基础诊断能力。

期望支持：

- 登录成功和失败事件。
- 验证码验证失败。
- CSRF 验证失败。
- 请求限流和自动封禁事件。
- 可疑上传或访问行为。
- 敏感操作审计。
- 安全日志脱敏。
- 自定义日志记录方式。
- 查询关键安全事件。
- 常见安全配置诊断。

不得将密码、访问令牌、Session ID、验证码答案等敏感内容直接记录到日志。

### 13. 可选高级能力

在基础安全能力成熟后，可根据成本与实际价值考虑：

- TOTP 双因素认证。
- 账号恢复码。
- 签名 URL 和临时访问链接。
- 基于风险的验证码或限流策略。
- 表单蜜罐及自动化提交检测。
- 可信设备管理。

这些功能不是必须独立成模块，也不应为了追求功能数量而增加维护负担。

## 三、旧项目兼容与迁移需求

SoSecurity 的一个主要用途是升级现有 PHP 项目的安全性。

需要特别重视旧系统的接入体验。

### 目标环境

- PHP 7.2～8.5。
- 原生 PHP 项目。
- 自研 PHP 框架。
- Symfony 项目。
- Twig 模板系统。
- 已有的 MySQL、Redis 和 PHP Session。
- Apache、Nginx、PHP-FPM 等常见运行环境。

### 迁移原则

1. 允许逐项替换旧安全实现。
2. 不要求一次性重构整个系统。
3. 不强制改变已有认证流程、数据库结构和路由机制。
4. 支持复用已有 Session、Redis 或数据库连接。
5. 不强制安装不必要的扩展或第三方服务。
6. 应尽量减少业务代码的修改。
7. 为常见的旧版安全实现提供迁移示例。
8. 对可能破坏兼容性的安全变更，提供观察、测试和回滚方案。
9. 配置异常或依赖故障不能导致敏感接口静默失去安全保护。
10. 不同模块可以逐步启用，不要求安装后立即启用全部功能。

特别重视现有登录、注册、密码找回、后台管理、文件上传和表单提交等场景。

## 四、配置与存储需求

所有适合配置的安全规则应提供合理的配置能力，避免将策略硬编码到业务中。

支持根据不同项目、环境和业务场景使用不同安全策略。

需要考虑多站点、多进程、并发访问，以及不同站点共用 Redis 或数据库的情况。

存储方案应由 Codex 结合功能特性合理规划。

期望能够支持 Redis、数据库及适当的文件存储方案，但不同存储后端必须满足相应功能所需的原子性、过期和并发安全要求。

对于不符合安全要求的存储方式，不应因为追求兼容性而默许其用于生产环境。

不要求所有模块都依赖同一个存储后端，也不强制安装 Redis。

## 五、PHP 与 Composer 要求

- 项目以 Composer 包形式发布。
- 使用规范的命名空间和自动加载。
- 支持 `composer require sohophp/sosecurity`。
- 核心代码兼容 PHP 7.2～8.5。
- 兼容目标 PHP 版本的实际 Composer 依赖解析。
- 尽量减少依赖数量。
- 避免引入大型框架作为必需依赖。
- 优先复用成熟、维护良好且许可证兼容的第三方库。
- 不自行实现已有成熟替代方案的高风险密码学算法。
- 对不兼容的第三方组件，允许提供可选集成或版本适配方案。

PHP 7.2 等旧版运行时已经停止官方安全维护。本项目要求保持代码兼容，但不能宣称使用 SoSecurity 后这些旧版 PHP 就具备了完整安全保障。

## 六、安全设计要求

参考 OWASP Cheat Sheet Series、OWASP ASVS 及相关成熟安全实践。

重点关注：

- CSRF 绕过。
- XSS。
- SQL 注入相关的安全边界。
- 暴力破解与凭据填充攻击。
- Session 固定与劫持。
- Token 重放。
- SSRF。
- 文件上传攻击。
- IP 欺骗。
- 代理信任错误。
- 并发竞态条件。
- 信息泄露。
- 日志注入。
- 拒绝服务与资源耗尽。
- 安全配置错误。
- 多租户或多站点数据隔离。

不要宣称单个组件能够全面阻止某一类攻击。

尤其需要明确，SoSecurity 不能替代业务授权检查、参数化 SQL、正确的 HTTPS 配置、服务器更新或基础设施层的安全防护。

安全应优先于使用便利性，但也要避免不合理的默认策略造成正常业务不可用。

## 七、质量与测试要求

SoSecurity 是安全相关基础库，因此测试质量必须高于普通功能组件。

要求：

- 完整的单元测试。
- 必要的集成测试。
- PHP 7.2～8.5 兼容性测试。
- 并发与竞态条件测试。
- 关键安全场景回归测试。
- 边界输入和异常路径测试。
- Composer 依赖安全检查。
- 静态分析和代码质量检查。
- 关键实现的安全审查。
- 适合旧项目的接入测试。

优先建立自动化 CI。

已停止维护的 PHP 版本应在隔离的测试环境中进行兼容性验证。

不能仅凭单元测试通过，就宣称整个组件库已经通过安全审计。

对于无法实际验证的环境或功能，必须明确标注。

## 九、架构与维护原则

不预先指定项目文件结构、类设计、接口布局或模块拆分方式。

由 Codex 根据完整需求自主研究并规划。

但必须遵循以下原则：

**高内聚、低耦合、职责清晰、避免重复实现。**

例如：

- 自动封禁属于请求限流和防暴力破解体系的一部分，不必单独开发 AutoBan 项目。
- 验证码可以复用已有的安全计数和风险策略。
- 各功能应尽量共用适当的基础能力，而不是建立多套独立计数、存储或日志机制。
- 不因功能名称不同就机械地创建新模块。
- 不为了未来可能存在的需求引入大量暂时无用的抽象。
- 保持对外 API 简单、清晰、可预测。
- 对安全敏感 API 和默认行为，应特别重视版本兼容性。

可以参考成熟 PHP 安全库的优秀实践，但不直接照搬大型框架的完整安全体系。

## 十、开发与交付目标

项目不要求一次性完成所有功能。

请 Codex 根据安全风险、依赖关系、实际价值及开发复杂度，自主规划合理的开发顺序、里程碑和版本。

优先确保基础安全功能可靠，并尽早让项目具备在真实旧 PHP 网站中使用的能力。

**第一项实际应用目标：**

能够在已有 PHP 网站中通过 Composer 安装 SoSecurity，逐步替换原有验证码、CSRF、登录失败限制和其他安全逻辑，在不重构业务系统的情况下完成安全升级。

**长期目标：**

建立一个稳定、可靠、开源、可扩展的 PHP Web 安全工具包，可以持续用于多个 PHP 项目。

不追求功能堆砌，而追求安全性、实用性、兼容性和长期维护质量。

## 十一、交给 Codex 的执行要求

请以本说明文档作为项目的初始产品需求。

1. 首先检查 GitHub 仓库和本地项目实际状态，不假设现有实现已经完成。
2. 研究需求涉及的安全标准、PHP 版本约束和适用的成熟方案。
3. 自主完成总体技术规划、安全威胁分析、功能边界划分和开发路线设计。
4. 自行决定项目架构、目录结构、接口、依赖、测试策略及版本里程碑。
5. 将重要架构决策及其理由记录到项目文档。
6. 在目标明确、没有重大阻碍时，自主推进开发、测试、审查及修复，不必反复询问普通技术实现细节。
7. 优先完成可独立验证、可实际接入旧项目的功能。
8. 避免重复造轮子，也避免没有必要的模块和过度设计。

10. 对于无法同时满足的要求，应说明权衡、风险和最终选择，不应默默忽略需求。

12. 每个里程碑交付时，提供实现说明、测试结果、兼容性状态、已知风险和下一步计划。

**最终要求：**

由 Codex 根据上述产品目标独立完成项目规划与开发工作。

本需求说明只约束项目的目标、能力和质量，不提前限制合理的技术实现方案。
