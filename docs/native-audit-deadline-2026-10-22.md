# 审计期限在 pending 前拒绝（2026-10-22）

上一批原始默认 MySQL 预算失败后，独立检查发现：`SqlSink::prepareState()` 只把调用者期限收紧到内部写入器，外层状态边界仍只检查较长的调用者期限。审计准备后较短预算已耗尽时，外层仍会先登记 pending，再由写入器拒绝。没有审计写入并不允许事后清除 pending。

用新建独立状态、审计1000毫秒／调用者10000毫秒及准备后等待1100毫秒复现：零审计记录，但见证从revision6/current变为revision7/pending。修复前断言失败保留于[before.log](native-audit-deadline-evidence-2026-10-22/before.log)，没有对该失败状态重试或续办。

修复仅在建立内部审计期限后，使用 `Deadline::restrictTo()` 将该较短期限同步给调用者。外层已有的写入前检查因此可以在 pending 前拒绝；不延长任何期限、不提高默认预算、不改变后续未知失败的处理。

这是可见的预算语义收紧：传给 `prepareState()` 的期限对象会收紧到审计期限；调用者后续阶段不能继续使用更长的原预算。公开类型仍275，签名不变。普通 SqlSink 调用不使用此准备接口，不受该收紧影响。

验证覆盖九版PHP的较短审计期限／较短调用者期限，两端普通SQL审计、单次准备写入和API清单；两端私有禁TCP MySQL及离线ZIP全新消费者另行记录。源码摘要、准确命令和失败日志见[证据目录](native-audit-deadline-evidence-2026-10-22/)。没有整轮运行含暂缓功能的bin/check.sh。

本修复不解释上一批PHP7.2管理认证失败，也不证明MySQL默认预算足以完成正常委托。完整候选、任意自定义提供器原生接入、默认预算可用性及历史失败仍开放。暂缓功能、生产访问、外部投递、提交、推送、部署均未执行；goal继续active。

最终定向结果：九版24/24、私有MySQL6/6、归档与全新消费者10/10、两端语法及shell检查7/7、PHPStan退出0，API清单275类型通过；见[result.json](native-audit-deadline-evidence-2026-10-22/result.json)。静态分析原有可选turbo扩展GLIBC警告保留。这些结果不抵销上一批正常委托的失败。
