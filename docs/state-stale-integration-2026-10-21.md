# F01 陈旧 current 的独立关闭入口

日期：2026-10-21（Asia/Shanghai）。本组继续原 P1／G4，不新增阶段或预算。修复的是完整旧备份导致 `current` 摘要不匹配，却无法进入原有仅接受 `pending` 的恢复链这一缺口。最终重新开放业务和完整 R1—R6 尚未完成。

## 状态与审批用途

新增 `LocalStateWitness::staleReview()` 和 `retireStale()`。前者只接受有效的 current 见证及实际不匹配的完整来源；健康 current、pending、closed 和 quarantined 均不能冒用此入口。原有 `retirementReview()`／`retirePending()` 继续只处理未决操作。

两条路径复用不可变 `StateRetirementReview` 值对象，但明确区分：

| 路径 | 审阅 purpose | 操作授权动作 | 审阅签名域 |
| --- | --- | --- | --- |
| 未知结果关闭 | `retire_unknown` | `state.retire_unknown` | `SoSecurity.Account.StateRetirementReview.1` |
| 陈旧 current 关闭 | `retire_stale` | `state.retire_stale` | `SoSecurity.Account.StateStaleReview.1` |

部署须显式允许新动作的准确资源类型、字段和恢复管理员角色；已有未知结果批准不能当成陈旧状态批准。实际独立密码／TOTP／会话、近期强认证、审阅后重新认证和一次性参数绑定授权继续由 `StateRetirementControl` 执行，不增加布尔批准回调。预览还要确认审批状态与业务 SQL／文件／见证物理域分离。

审阅绑定原 current 的修订、操作编号、原意图、可信摘要和实际观察摘要、控制器、用途、时限及随机尝试号。关闭前后反复核对准确来源、见证和当前审批人；如果业务数据已修复回可信摘要，旧的陈旧状态批准也不能继续关闭它。

## 不采用当前数据

成功只把旧权威永久转换为 closed。原可信摘要、修订和原操作意图保留，另保存关闭批准回执；观察到的旧备份摘要仅作为审阅材料，绝不赋给可信 digest，也不调用业务恢复或重放。

随后可以继续原有独立批准的新代际隔离。新代际仍为 quarantined，保留原可信摘要和前序意图；账号固定处置完成后也仍隔离，不因此允许旧会话、密码或恢复码进入业务。

首个 current 检查点也可能发生仍可按声明读取的变更或旧数据覆盖，不能为此虚构 pending 或未知操作。因此单独支持修订 1 的陈旧关闭，继任隔离从修订 2 开始；账号／因子处置审阅的结构下限相应允许这个实际可达路径，签名、代际、准确根、角色和一次性授权核对保持。修订 1 的未知结果批准仍不合法。

这扩展了格式 2／3 的合法状态语义及审阅用途，没有增加回执字段或更换封存布局。旧读者可能拒绝新的关闭回执，不能混用部署；旧业务工作进程必须按原计划停止／栅栏隔离，不能靠这项语义扩展声称它们已全部退出。

## 固定验收

准确命令与源码见[执行记录](state-stale-evidence-2026-10-21/execution.json)，接口及原有成员保持见[接口核对](state-stale-evidence-2026-10-21/api-compatibility.json)。为复用真实完整备份，将既有七表／文件备份帮助方法移入测试支持文件，方法体字节保持一致，见[移动核对](state-stale-evidence-2026-10-21/backup-helper-move.json)。

新增正常检查实际完成：登录并备份七张声明 SQL 表和认证文件，撤销会话后联合恢复全部旧数据；旧凭据先在业务访问前拒绝；独立恢复管理员通过重新认证及新用途一次性批准关闭陈旧 current，再进入新隔离代际。另有首个检查点的健康拒绝、陈旧关闭、继任隔离和账号固定处置，最终仍禁止业务调用。

固定拒绝检查覆盖用途／一次性授权不匹配、审批后来源变化、审批人撤权／停用／过期、篡改选择、预算拒绝、数据已修复、关闭持久回执丢失、关闭后撤权，以及 pending 必须沿用旧路径。原未知关闭、继任、不可变审阅、四类完整备份及物理因子部分效果续办纳入受影响回归。

首次固定 22 条命令中，20 条两端运行时／API 检查和 1 条完整源码静态分析退出 0；合并的 MySQL 控制器在四组测试均输出通过后达到 240 秒外层上限，退出 124，原始失败完整保留。只按运行时拆分该 MySQL 项复验，准确终态见[补充记录](state-stale-evidence-2026-10-21/mysql-followup.json)，两次分版复验均退出 0、来源哈希一致；三次临时实例目录均已移除。首次超时残留的已停止目录经所属标记和进程核对后单独清理，见[清理记录](state-stale-evidence-2026-10-21/initial-timeout-cleanup.json)，不会改写首次失败。静态分析存在既有可选 turbo 扩展的 GLIBC 启动告警，分析器自身退出 0、无代码错误。

MySQL 控制器只创建独立 Unix socket、禁 TCP 的临时实例；本组含固定账号处置，需要专用测试账号的全局 TRIGGER 元数据可见性。权限仅授给该临时实例，不读取或更改宿主业务数据库，不代表普通生产账号已经具有完整依赖可见性。PHP 7.2 使用已有私有 sodium／原生单调时钟，不能写成未增强系统 PHP 的完整通过。

检查通过并完成来源、接口和清理核对后，停止本组扩测；交付核对见[证据核对](state-stale-evidence-2026-10-21/delivery-check.json)。

## 最终恢复仍需完成

这不是最终恢复提交。结构损坏到无法按声明有界采集的来源，不得跳过检查来走本入口，仍需准确受控修复。仍须完成所有声明账号／因子／会话／一次性授权的完整处置，旧工作进程关闭与新进程注册、通知和队列准确对账、恢复审计耐久、新可信代际／来源的明确提交，以及恢复后真实新凭据登录成功而旧权限不复活。不得添加“采用当前摘要”或跳过隔离的快捷方法，也不得把仍 disabled／quarantined 的状态当成安全可用的最终验收。

其他授权入口、声明后端和原生 HTTP／浏览器接入继续属于完整 G1／R1—R6。SMTP、第三方 OIDC、实体设备、目标代理／WAF、远端 CI、独立复核和最终九版整轮，本组未执行；未提交、推送或发布。
