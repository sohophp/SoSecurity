# CSRF 与验证码的存储等待到期检查

本批实际复现：CSRF 或验证码在 verify 开始时有效，AtomicStore 读状态后或提交消费后等待至到期，原实现仍返回 true。两个原始失败分别保留在 [before.log](csrf-time-evidence-2026-10-22/before.log) 和 [captcha-before.log](csrf-time-evidence-2026-10-22/captcha-before.log)。

CsrfTokens 与 Captcha 现在记录最终存储回调匹配的到期时间，在存储返回后再次读取时钟；恰好到期也返回 false。回调重试会清除上一尝试的匹配记录，不在存储回调中新增时钟调用。已消费的证明不会因最终拒绝恢复、续办或重试。验证期间的时钟回拨、负时间、异常或错误类型统一抛出固定 csrf.clock／captcha.clock StorageException，无底层异常链或私密消息。发行路径和存储结构未改变。

- [callers.json](csrf-time-evidence-2026-10-22/callers.json)：九版密码重置示例及实际请求预算调用顺序，共 18 条命令全部通过。密码重置使用独立内存 SQLite，不执行账号恢复启用、跨代工作进程交接或未知回执续办。
- [static.log](csrf-time-evidence-2026-10-22/static.log)：PHPStan 退出 0；环境既有可选 turbo 扩展 GLIBC 警告保留。相关 git diff --check、bash -n 通过。
- [source-sha256.json](csrf-time-evidence-2026-10-22/source-sha256.json)：本批运行时代码、测试与检查入口摘要。API 反射维持当前候选 271 类型，没有改写候选。

## 范围和剩余事项

这是定向测试，不是全项目验收。本批未改 SQL 实现、发行或安装行为，未重跑私有 MySQL／归档消费者安装；此前专项通过记录不算本快照的重新验收。时钟故障现在呈现上述固定原因码，依赖原始 Clock 异常的调用方需适配；正常公开方法签名及数据格式不变。

工厂源码复核还确认：Security::csrf／captcha 仍使用 store('tokens')，没有原生完整见证连接；独立请求预算的隔离不能自动证明一次性请求证明已接入保护图。本批仅修复时间判断，未把此接入缺口宣称完成。Security::leases 的 apiStore 仍在保护模式明确拒绝；通知／Outbox 写入者的完整清单仍需核对。它们与此前未解释的 PHP 7.2 持续时间超时分别保留，不将其合并为已修复。

没有提交、推送、部署、生产数据库访问或外部投递。暂缓能力及外部验收继续保留；同范围 goal 为 active。
