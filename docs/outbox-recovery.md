# Outbox接收端检查点与恢复

这是[原生Outbox接收适配](outbox-native.md)的显式本地SQLite恢复协议，不改变库的公开API。接收端把业务唯一账本及投影绑定到已封存根记录，再用独立持久数据库记录写前意图。正常请求不能初始化、采用缺失历史或根据旧备份重置队列。

新增[对账取消](outbox-reconciliation.md)后，永久取消账本也进入同一封存历史与独立检查点，取消不创建业务投影。首次取消推进业务根为格式 2，需停止旧进程并显式安装示例增量 DDL；受控恢复可重放最后一个已封存取消，仍需当前对账管理权限及原事件关联。部分删除取消表记录不能被恢复命令直接确认。

## 两份数据库与外部代际

- 业务数据库新增 `outbox_example_receiver_root`，与业务唯一账本、投影在同一事务提交；安装[接收业务结构](../resources/sql/outbox-example-receiver-sqlite.sql)。
- 独立数据库安装[检查点结构](../resources/sql/outbox-example-checkpoint-sqlite.sql)，只保存上一根、下一根和最后一个事件的原始正文／稳定投递编号。SQLite须持久文件、启用日志及FULL／EXTRA同步。检查点中的正文是原始私有内容，封存不提供加密。
- 配置增加 `checkpoint_database` 和 `checkpoint_lock`，均为已存在的规范绝对路径。数据库与锁文件0600、父目录0700，位于真实Web根外，拒绝符号链接、相同文件及硬链接别名。锁文件由部署创建，应用不自动补建；单次获取锁最多等待1秒。
- 检查点必须有独立的可信备份／恢复顺序，不能随业务库一起回退。仅在同目录创建另一个数据库文件并不构成异地灾备。`epoch`保存在两份数据库之外，变更时须传播到所有接收进程。

每次操作重新核对当前配置和数据库／锁文件的设备及inode，防止常驻进程持旧PDO连接继续确认已经替换的文件。恢复期间必须停止普通接收和管理进程，释放PDO连接，并在维护互斥下更换文件；文件身份复核不授权运行中替换SQLite文件。

该协议在以下信任前提下检测回退：独立检查点或外部代际至少有一项保持可信、未随业务库回退。两份数据库、全部配置和外部恢复记录同时回退时，单靠HMAC无法证明真实最新历史。部署人员仍须维护可信恢复记录和业务对账，不能承诺跨系统恰好一次。

封存范围是业务根、独立账本及投影，不包含宿主账号、权限、路由和拥有者表。权限变化会按当前权威表拒绝，但只有权限表被回退、业务根保持相同时，业务检查点不能证明权限已回滚。恢复这些表时，宿主必须从当前权威来源重新核对权限，并保留独立的身份版本／部署代际；不能直接采用旧备份中的启用状态和角色。HTTP请求每次重新读取这些表不等同于权限历史的防回滚证明。

现可显式配置[独立权限源](outbox-authority.md)，将这些查询移到不随业务库恢复的只读来源。已有业务备份内的权限表不再参与授权；当前来源撤权时，普通投递、管理及已知转换恢复继续拒绝。独立权限库本身的时效与恢复仍由宿主管理。

## 正常提交与中断

验签、当前路由／拥有者验证及预算通过后，在全接收端互斥下执行：

1. 核对已提交检查点、业务根及完整业务账本／投影；最多1000条，每个返回字段在SQL端按类型和实际字节数限制。
2. 在独立检查点数据库先提交 `prepared` 意图，封存上一根、预期下一根及原始事件。
3. 在处理组件拥有的业务事务中，同时提交业务唯一账本、投影和下一根；SQL回调内不写独立检查点，不执行网络或请求预算副作用。
4. 确认业务根及完整历史匹配后，把检查点提交为 `committed`。再次核对当前身份、路由、拥有者、签名和代际后才返回确认。

这两份数据库没有分布式原子事务。中断可留下明确的prepared状态，普通请求此时返回503，等待受控恢复。

| 数据库状态 | 普通请求 | 显式恢复 |
| --- | --- | --- |
| committed检查点与当前业务根／历史一致 | 当前授权下继续 | 幂等返回未发生恢复 |
| prepared检查点，业务仍为上一根且历史一致 | 拒绝确认 | 重放封存的最后一个事件，或完成初始化／代际切换 |
| prepared检查点，业务已是下一根且历史一致 | 拒绝确认 | 只完成检查点，不再次产生业务 |
| committed检查点，业务恢复到恰好上一根 | 拒绝确认 | 仅根据封存意图补回这一条已知转换 |
| 更早备份、部分表恢复、根／投影不一致、单独旧检查点、密钥缺失或代际不符 | 拒绝 | 拒绝采用或清空状态，转业务对账与权威备份恢复 |

检查点只保留最后一个转换，不是完整事件日志，不能从任意旧备份重建所有业务。业务恢复后，独立账本可证明既有提交；即使原Webhook接收／处理历史仍缺失或有旧租约，重复投递也不增加投影次数，不伪造处理状态为成功。

## 显式管理

[接收管理命令](../examples/outbox-receiver-admin.php)只在CLI直接执行，导入无副作用，HTTP访问404。它使用受控OS服务账号、私有配置及当前数据库 `receiver_admin` 角色；业务重放还要求当前 `receiver_worker`、发布方路由和拥有者有效。配置中的服务账号版本变化、撤权或禁用都会拒绝旧身份。无额外命令参数可替换操作者。

先切换到接收方的私有配置，再执行：

```sh
php examples/outbox-receiver-admin.php --initialize
php examples/outbox-receiver-admin.php --status
php examples/outbox-receiver-admin.php --recover
php examples/outbox-receiver-admin.php --rotate-epoch=<原64位epoch>:<外部保留的原root_hash>
```

`--initialize`仅允许两套安全历史、业务账本／投影和检查点均为空；已初始化且一致时返回false。旧候选示例的非空未封存接收库不能自动采用，需宿主提供经过权威业务对账的迁移，不能删除历史后运行初始化。

`--status`只返回epoch、sequence、entries、root_hash，不返回原始正文、密钥或私有路径。`--recover`幂等，并严格使用已封存的原始正文／投递编号；不接受新正文、替代编号或“视为已发送”的参数。命令错误只输出固定错误码和非零退出状态。

代际切换顺序：停止接收及管理进程并排空在途请求，确认检查点已committed，将 `--status` 的epoch及root_hash保存到业务备份之外的可信发布记录；再更新外部配置为新epoch，按旧epoch及可信root_hash执行旋转，然后启动新配置进程。旋转保持业务条数和身份不变，仅推进检查点序号及代际。不得从待恢复的旧数据库临时计算摘要，冒充外部可信发布记录。

若更改外部配置时仍有旧代际prepared意图，普通恢复与旋转均拒绝。先停止全部进程，在部署控制下临时恢复原配置，完成已知意图并重新保留可信检查点，再按上述顺序切换；不能改数据库中的epoch或清空检查点。

业务库恢复后保留独立最新检查点，先运行 `--recover`，验证当前检查点与权威业务条数，再恢复接收。超过一个转换的旧备份需要完整的权威业务恢复／对账；该命令不会自动跳过缺失事件。接收代际和检查点不自动关闭发送方过期dead消息；现有签名终态证据与显式对账处置见[超期对账](outbox-reconciliation.md)，完整R4.3继续。

## 密钥与兼容边界

业务根和独立检查点使用接收端封存密钥，与投递签名密钥分离；每次读取当前密钥快照。检查点仍引用上一根时，必须保留该根的旧封存密钥。Webhook接收／处理历史也可能需要旧密钥，须分别完成其显式维护；不能仅见新检查点已写入就移除旧密钥。缺失旧密钥时拒绝重新封存，恢复需要可信原密钥和历史。

库核心仍支持SQLite／MySQL，本恢复示例只实现单机SQLite和文件互斥。多主机接收、跨机锁、生产备份编排及真实灾备演练需要宿主实现并单独验收。本阶段本地测试不能代替生产恢复或独立安全审查。

## 验证入口

`php -d memory_limit=8M tests/outbox-recovery.php`使用自己创建的私有临时数据库，执行真实文件备份／恢复、四个有明确就绪标记的活跃子进程SIGKILL、初始化／代际提交前后异常、当前权限、部分恢复、旧配置／旧文件句柄、锁／事务／耐久性拒绝，以及16MiB异常字段。所有子进程均确认终止并回收。

`python3 tests/outbox_native.py <PHP运行时>`另通过实际HTTPS入口验证旧备份503、CLI恢复、原投递编号去重、当前代际和管理CLI的HTTP拒绝。完整已执行结果及源码快照见[验证记录](verification.md)。
