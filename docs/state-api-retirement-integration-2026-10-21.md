# G4 旧版 API 密钥的主体代际处置

日期：2026-10-21（Asia/Shanghai）。继续原 P1／G4，不增加阶段或预算。本组为旧版 `ApiKeys` 引入永久主体（subject）代际（epoch），一次准确批准可使所选服务 namespace 中该主体的全部旧密钥失效，包括已过期但仍保留在备份中的记录。不改变账号字段、不采用当前来源为新基线，也不解除隔离；完整 G4／F01／R1—R6 仍开放。

## 令牌与兼容语义

客户端令牌格式仍为 `sosk_<id>.<secret>`。原服务在没有代际标记时继续读写记录格式 1；原构造参数和公开方法签名保持。处置后永久标记保存在同一真实 FileStore 的 `api-key-epoch:SHA256(subject)`，容器 `expires=0`，值为固定格式 1 的主体和 64 位十六进制代际。正常读取不会创建、重置或自动修复标记。

| 密钥记录 | 当前标记 | 结果（仍须通过令牌摘要、授权范围及到期检查） |
| --- | --- | --- |
| 格式 1 | 不存在 | 保留旧兼容行为；不代表能够抵御备份回放 |
| 格式 1 | 存在 | 拒绝；不能通过 `rotate()` 洗成新代际 |
| 格式 2 | 代际相同 | 按原验证规则处理 |
| 格式 2 | 缺失或不同 | 拒绝，不降级接受 |

处置后 `issue()` 生成绑定当前代际的格式 2 记录，`rotate()` 保持其代际。正常签发和轮换在提交后复查代际，期间变化返回明确未知结果；认证复查密钥字节及代际。随机数、时钟、其他 key 的读取均不放进可重试的 AtomicStore 回调，回调只校验和提交确定数据。不声称两份记录构成跨 key 原子事务；保护模式仍要求外层准确见证串行化所有已登记写入者。

旧版 `ApiKeys` 的主体标签没有租户或账号仓储契约。本组不从标签推断账号归属：批准明确绑定实际 API 服务 namespace、主体和物理位置。其他主体、其他 namespace 的密钥保留；若启用多个旧 API 服务，每个实际域须分别声明和处置。

## 原生批准与固定写入

新增 `StateApiKeyRetirement`、`StateApiKeyReview` 和内部 `StateApiKeyManifest`。`prepare()` 要求准确 quarantined 权威、完整具体来源、其覆盖的 FileStore、确实使用该同一存储与时钟的 `ApiKeys`，并生成固定新代际。纯配置方法 `ApiKeys::stateEpoch()` 只返回原生坐标和固定字节，不写入或授予权限。清单只保存原标记 SHA-256／缺失状态及新标记，不保存 bearer 令牌、旧密钥摘要或密钥清单。

`apiKeyRetirementReview()` 绑定准确根、代际、来源、当前字节和计划；`retireApiKeys()` 要求独立恢复管理员具备 `state.api_keys.retire`，审阅后真实密码／TOTP 重新认证，以及参数绑定的一次性批准。权限、时限、来源及进程／Fiber 所有权在效果边界复查。先持久 pending，再通过原固定条带、私有有界暂存、原始字节 CAS 和文件／目录持久化写入永久标记。

`FileStateSnapshot::canStoreFile()` 只检查物理容量，不预留或删除数据；已过期正式文件仍计入数量。新标记缺失且容量已满时，计划在批准消费／pending 之前拒绝；覆盖已有位置不要求新增槽。未知外部并发或持久化错误仍不能当作已确认无效果。

重命名前后或最终预算确认失败保留原清单。`resume()`、`apiKeyResolutionReview()` 和新的 `state.api_keys.resolve` 批准只能续办已封存效果；不得复用旧批准、替换服务／主体／epoch，或接受第三种字节。重复未知结果也不生成另一个代际。恢复审计保留原始审批和每次续办，根仍 quarantined，原可信摘要保持。

新增 API 处置清单／审阅为格式 1，沿用现有见证格式 3 和审计记录格式 2，不含 DDL 或新强制依赖。旧读取器不理解新回执，旧 API 代码也不会检查标记；必须升级并停止旧工作进程，禁止混合部署后宣称旧密钥已失效。

## 有限验证

**已执行并通过：固定 27 条命令全部退出 0，输入 SHA-256 保持一致，四次私有 MySQL 实例均已关闭并清理。** 两端两个 SQL 后端各通过正常处置 52 项、部分效果续办 215 项、配置／篡改拒绝 56 项、完整文件回放 5 项；12 个真实 SIGKILL、新进程恢复场景各 37 项通过。两端原 API 各 200 项、并发代际 10 项、容量 6 项、原文件扫描／会话处置／公开接口及全源码静态分析通过；保留既有可选 turbo 扩展 GLIBC 加载警告。

固定 27 条命令：PHP 7.2／8.5 各执行原 API、代际交错、物理容量、原文件扫描、三组原生处置、备份回放、原会话处置、公开接口及三个真实终止点；两次私有 MySQL 功能组、另两次私有 MySQL 终止组；一次全源码静态分析。准确输入和结果以[执行记录](state-api-retirement-evidence-2026-10-21/execution.json)、[交付核对](state-api-retirement-evidence-2026-10-21/delivery-check.json)为准，结束后停止本组扩测，不重跑历史快照或开发期间九版整轮。

普通 API、容量和文件来源检查保持 8 MiB；完整受保护图使用 16 MiB。PHP 7.2 使用私有 sodium／posix 和原生单调时钟，不称为未增强系统运行时完整通过。控制器每组外层 600 秒、一般单项 240 秒，SDK 原期限不变；系统时钟倒退仍拒绝，不静默钳制。MySQL 均为控制器自建、禁 TCP、私有 Unix socket 的临时实例，不连接业务数据库。

功能检查使用实际 API 令牌和复制后的真实原始文件；在隔离对照中将时钟设为零，使已过期旧密钥重新具备到期条件，证明拒绝源于代际而非仅到期。新代际仍能签发和轮换。删除标记的去防护对照会使格式 1 密钥重新有效，格式 2 则拒绝；实际完整来源见证在恢复全部旧文件／丢失标记时于业务回调前拒绝，证明永久标记不能单独替代独立新鲜性权威。

真实终止由控制器发送 SIGKILL，核验信号退出，再用独立 PHP 进程重新打开 PDO、来源、见证、审计和审批服务，覆盖重命名前、重命名后和最终确认前。新批准完成原同一代际，原批准拒绝；不复用 fork 继承的连接或序列化的服务对象。

原 API 200 项回归和代际交错 10 项预检通过。首次静态检查因永远抛异常的帮助方法缺少 `@return never` 说明而失败，已补准确控制流说明；首次终止测试因测试支持文件重复加载失败，改为 `require_once`。原日志和失败源码副本保留，正式冻结检查另列。接口核对见[记录](state-api-retirement-evidence-2026-10-21/api-compatibility.json)：原有 259 个公开类型及全部原成员签名保留，当前 261 个公开／59 个内部类型。
