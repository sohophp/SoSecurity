# 审计告警窗口恢复：缺口确证与最小方案

日期：2026-10-23。本文只记录当前源码的只读核对和后续设计，**恢复功能尚未实现，建议入口尚未冻结，未执行新功能测试**。它不关闭 R4.6、当前 goal 或稳定版验收。

[原计划 R4.6](full-plan-2026-10-21.md#L88)要求告警去重、投递、幂等回执及保留期外恢复；[SQL 审计专项](sql-audit-integration-2026-10-22.md#L43)也保留了“保留期外回放／恢复”。这里指审计／告警旧窗口数据，不是暂缓的账号恢复，不能自动归入暂缓范围。

## 当前代码能证明什么

以下链接定位本次核对时的源码；源码改变后应重新核对，不能把文件存在或测试断言存在当作当前执行通过。

| 事实 | 源码依据及影响 |
| --- | --- |
| 指标策略没有写入审计事件 | [MetricsSink 的策略摘要](../src/Audit/MetricsSink.php#L57)绑定事件分类、阈值、容量、窗口长度及可选保留数量，保存在指标状态；[SqlSink 的策略摘要](../src/Audit/SqlSink.php#L43)只绑定日志容量与保留期，不能替代原指标策略。 |
| 指标计数不等于持久日志行数 | [MetricsSink](../src/Audit/MetricsSink.php#L124)先累计已准入尝试，再调用下游日志。日志提交失败仍可能留下指标；[现有测试源码](../tests/audit-sql-pipeline.php#L72)明确区分三次指标尝试与两条持久日志。 |
| 现存时间字段不能确定原指标窗口 | [AuditLogger](../src/Audit/AuditLogger.php#L58)记录 `time()`；MetricsSink 使用自身 `Clock`；[SqlSink](../src/Audit/SqlSink.php#L108)另存接收时的 `recorded_at`。三次取时可能跨窗口，直接调用日志接收器也不能提供原指标取时。 |
| 审计事件没有原窗口元数据 | [SQL 表结构](../resources/sql/audit-sqlite.sql)保存 `site/sequence_no/recorded_at/expires_at/record`；正文是固定的 `time/event/scope/subject/context`，没有原指标策略、分类和窗口边界。 |
| 现有补采只读仍保留的窗口 | [MetricsSink::inspectRetained](../src/Audit/MetricsSink.php#L139)返回指标状态仍保存的窗口；[AlertOutboxPublisher::publish](../src/Audit/AlertOutboxPublisher.php#L36)仅遍历这些窗口。 |
| SQL 历史查询不恢复过期数据 | [SqlSink::records](../src/Audit/SqlSink.php#L185)每页最多100行，只返回 `expires_at > now` 的记录。日志仍在 SQL 保留期，并不补出其未保存的指标尝试和策略。 |
| 原告警身份和期限不能重置 | [Publisher](../src/Audit/AlertOutboxPublisher.php#L39)以站点、类别和原窗口生成固定 ID；[Worker](../src/Audit/AlertOutboxWorker.php#L80)校验固定正文及原创建时间；[Outbox 入队](../src/Outbox/SqlOutbox.php#L171)仍按原 `message_age` 拒绝过旧事件，相同 ID 的不同正文会冲突。 |

因此，**不能仅统计仍存在的旧 SQL 审计事件，就宣称准确恢复原 Metrics 窗口或原告警**。它最多是按另外指定规则统计已持久化事件，不等于恢复原尝试计数、原分类和原阈值判断。

上述测试文件只作为既有语义的源码依据；其中包含未知回执重投场景，本文不授权执行整个文件或把它直接并入后续恢复测试。

## 唯一最小方案：显式闭合窗口检查点

只为启用后、已及时保存检查点的窗口增加有限恢复，不设计通用外部档案协议。

1. 在原指标窗口仍可读取时，显式保存已经闭合的窗口。调用方须预先启用足够的指标保留；当前默认 `retainedWindows=0` 不因此改变，也不能保证在窗口消失后补存检查点。
2. 检查点绑定原站点、原指标策略、窗口起止、四类计数、总数及原阈值判断。策略信息须足以核对固定计数、窗口长度和阈值，不能用恢复时的新配置替换历史策略。只接受组件读取并验证的窗口，不接受请求提交的“已授权快照”。
3. 通过显式安装的独立 SQL 窗口存储保存检查点，具有固定格式、字节／条目／保留预算、严格表结构及独立当前读写授权。保留现有审计事件格式和表，不把新结构塞入旧日志正文，不隐式建表或迁移旧数据。同站点同窗口重复保存须完全一致；冲突拒绝，不能覆盖旧检查点。
4. 检查点 SQL 写入放在 `AtomicStore::transact()` 回调之外。只保存闭合窗口，不移除或改写原指标；确定失败时保留原状态，提交未知时抛错，不自动重放。调用时可用的来源和已确认检查点必须分别记录。
5. 恢复只分页读取仍在 SQL 保留期内的检查点，核对准确站点／策略、当前读取权限、Outbox 发布权限和共享期限。恢复仅入队，不重建当前 Metrics 计数，也不领取、重新排队或结算已有投递。
6. 生成与原 Publisher 相同的消息 ID、正文、创建时间和投递幂等身份；重复入队沿用现有 Outbox 契约。不得改用恢复时间生成新 ID，不延长原 `message_age`，不放宽权限或预算。

以下名称仅是建议入口，**不是已存在或已批准冻结的公开契约**；类名、参数、错误码及实际 API 差异须在实现时逐项审查：

- `MetricsSink::checkpointClosedWindows(...)`：有界保存当前仍可读取的闭合窗口。
- `AlertOutboxPublisher::publishRecordedWindows(...)`：从准确检查点来源分页补入原告警消息。

应沿用既有窗口数量上限和有界分页，不增加全量扫描入口。窗口存储可以是小型可选 SQL 组件；是否新增公开类型或方法以实际实现清单为准，不预先改写 API 候选。

## 可恢复范围与明确拒绝

可恢复范围是：**原指标窗口已离开 Metrics 保留范围，但准确检查点仍存在于 SQL 保留期内，且原消息仍在 Outbox 准入期限内**。

- SQL 事件仍存在、但从未保存准确窗口检查点：不能保证恢复原指标，须明确报告缺少恢复来源。
- 检查点已到期、被删除或无法验证：不能把空页解释成“历史均已处理”，也不能伪造零计数。
- 原日志与检查点均已删除且没有可信来源：不可恢复，明确记录缺失，不创建外部档案或导入协议来扩大本批。
- 原消息超过 `message_age`：沿用到期拒绝；不回拨时间、不提高期限、不生成替代 ID。
- 原策略或站点不匹配、同窗口内容冲突、授权失效、来源损坏或预算不足：默认拒绝，不自动迁移或采用新规则重算。

## 后续实现的有界交付条件

本地子关口只交付上述检查点及补入队能力，并完成以下检查：

- 先以新建测试数据确认旧 SQL 事件缺少策略／原窗口且可能少于指标尝试，证明不能直接精确重建；保留失败或明确不支持证据。
