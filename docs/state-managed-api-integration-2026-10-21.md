# G4 账号 API 凭证的原生退役与准确边界

日期：2026-10-21（Asia/Shanghai）。继续原 P1／G4，沿用 31 项、80 个有效工作小时上限，不增加阶段或自动延期。本组把账号绑定的 `CredentialRegistry` 纳入既有 API 固定效果处置协议，并阻止绕过显式受保护边界直接调用服务。完整 G4／F01／R1—R6 保持开放。

## 准入与实际服务图

`CredentialRegistry` 构造函数只增加末尾可选 `StateBoundary`，原参数及原令牌格式保留。保护模式必须使用同一原生密码提供方、受管第二因子对象、会话注册表、时钟和具有语义权威的边界；仅配置相似不视为同一服务。八个有状态公开方法在读取存储、查询身份或调用宿主保护／授权回调前检查准确作用域与活跃边界。保护绑定之前创建的旧服务对象也在调用时检查，不因缓存而绕过。

这只提供显式上下文约束。`Security::apiCredentials()` 等公开保护工厂仍拒绝未接线能力：现有管理认证会更新会话，而请求保护随后才执行，尚未实现宿主拒绝在 pending 前完成的只读准入。测试中的显式 `boundary->run()` 不代表真实 HTTP／CSRF／角色拒绝顺序已验收。

## 固定原生账本处置

`StateApiKeyRetirement::prepareCredentials()`／`resumeCredentials()` 复用原强批准、耐久审计、pending、CAS、固定暂存与未知效果续办。必须明确实际 API 服务、被完整来源覆盖的 FileStore、同一时钟、作用域和主体；不从标签推断租户，也不允许任意文件或业务回调写入。

新清单格式 2 绑定 `account_credentials`、scope、原始计划时间、准确物理账本、原字节摘要和唯一 after 字节。after 为原生空 `CredentialState`：永久容器、新 32 位十六进制 epoch、固定身份哨兵、原策略摘要及空 entries。身份哨兵不是可用身份。续办保留相同时间与 epoch，只接受原 before 或原 after；不能采用第三种字节、新服务或新策略。审批和审计仍使用 `state.api_keys.retire`／`state.api_keys.resolve`，未知结果必须重新强认证并取得新批准。

原 `ApiKeys` 清单格式 1、方法签名和指纹域保持，新旧类型不能互换。此组不变更 SQL 结构、来源 Profile.3 或见证根格式。清单读取器和 API 工作进程必须升级或停用，不能混合旧工作进程后声称旧授权全部失效。

完成保留 quarantine 和原可信摘要，不改账号字段、不启用账号，也不等于完成其他授权或一次性证明退役。
