# 地址变更申请及完成的原生准入

本批补齐地址变更在保护模式下的意图准备、申请、完成意图准备及最终改址。最终改址是已登录账号通过旧／新邮箱证明后更改地址，不是暂缓的账号恢复启用。

## 实际变化

`AddressChange` 新增 `proposalFor`、`requestFor`、`completionProposalFor`、`completeFor`，首参数为准确的 `StateAccountPolicy`，其余参数与对应旧入口一致。旧入口及旧签名保留，继续要求显式外层边界；新入口自行进入准确边界，不能再嵌套调用。使用真实受保护会话、普通 `Grants` 的同一存储／会话／时钟及纯 `RolePolicy`，自定义有副作用的授权提供器不能假冒只读准入。

公共请求额度在锁前收取一次，整个操作复用同一时限和预算编号。锁内先从完整来源读取实际会话、当前账号及地址版本，认证账本根和历史；完成操作另核对当前申请指针、双邮箱证明和期限。随后检查当前对象／字段权限及一次性授权的签名、状态、账号、会话和期限，才允许写入 pending。实际业务仍复用原有事务和授权消费路径，并复核原始身份、意图及会话。

原业务请求守卫增加只读 `admission` 阶段；宿主应允许其重复调用，不在该阶段写业务数据。异常转换为固定 `account.authority`，不携带原始异常链；显式拒绝为 `account.denied`。守卫对引用参数的重赋值不能更换已准备的目标。原有请求及完成阶段仍执行。

无效会话、缺少角色、错误授权秘密、已使用授权、未完成邮箱证明及准入期间过期在 pending 前拒绝。真实授权凭证的意图错配仍由原业务消费并销毁，保留 pending；不能提前把它转成无效果拒绝而恢复凭证。请求或改址已经提交后守卫拒绝，同样保留已提交状态及 pending，本批不续办。

只读账本使用内部 `SqlTransaction::forObservation`。该路径不取得 MySQL `FOR UPDATE` 锁，仍认证完整账本；写 SQL、账本写入和宿主回调均拒绝。普通账本继续要求活动保护边界，没有开放原始写入入口。

## 验证与兼容

首轮真实入口失败为 `account.state_required`，定位到只读账本仍调用写入边界检查；修正后 PHP 8.5 的正常流程和四种拒绝／提交后失败场景通过。另补充只读单元的真实账本写入拒绝测试；第一次测试使用了错误账本命名空间，失败日志保留，修正测试预设后通过。

公开类型仍为 272，本批增加 10 个方法，没有改变现有公开签名；内部账本和 SQL 单元未加入公开清单。准确增量见 [API 核对](native-address-actions-evidence-2026-10-22/api-review.json)。测试使用真实本地新账号、密码认证、重新认证、一次性授权、双邮箱证明、版本更新和会话失效；通知只加密写入本地队列，不外部投递。

全部结果以 [证据目录](native-address-actions-evidence-2026-10-22/) 的矩阵、消费者和 MySQL 日志为准。此前 PHP 7.2 未解释的提前超时保持开放，不用新增专项通过覆盖历史失败。完整项目验收、其他产品入口、真实 HTTP／邮件／外部提供器及正式发行均未据此通过；跨代交接、未知结果续办和最终恢复启用仍暂缓。

最终本批结果：PHP 7.2—8.5 九版定向矩阵 **89/90 通过**。PHP 7.2 的 expiry 命令在约 0.769 秒发生 `sql.timeout`，目标场景未完成，底层提前超时原因未确认；首次日志保留，没有重跑覆盖。两端私有 MySQL **12/12 通过**，其中 PHP 7.2 使用既有原生单调时钟及 sodium 包装；默认时钟下的失败未因此关闭。归档／离线全新消费者 **14/14 通过**，八个运行时文件摘要与安装包一致；消费者已清理，专属 MySQL 进程已退出。两端语法 **20/20 通过**，完整 PHPStan 无错误，可选 turbo 的 GLIBC 警告保留。测试期间的输入摘要未改变；准确命令、结果和兼容清单见 [result.json](native-address-actions-evidence-2026-10-22/result.json)。

继续核对源码确认 `Security::leases()` 与 `Security::quarantine()` 仍通过 `apiStore()` 在保护模式明确拒绝，不能当作已接入。它们及其余尚未分类入口保持开放；本批不将 goal 标记完成。
