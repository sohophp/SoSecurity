# SQL 事务所有权与宿主事务加入

状态：R4.3 的内部基础设施。`Support\SqlTransaction` 与 `SqlTransactionGuard` 属于内部实现，不列入公开API。后续已增加[Outbox核心候选](outbox.md)、原生发送／接收及受控检查点恢复；显式[超期对账核心](outbox-reconciliation.md)也加入宿主事务，原生签名证据／取消栅栏及完整出站验收继续。

## 两种事务边界

| 内部模式 | 前置条件 | 提交责任 | 成功结果 |
| --- | --- | --- | --- |
| `run()` | 实际空闲的 PDO 连接 | 组件提交自己的事务 | 本次组件事务已确认提交；仍可能在提交后复核或响应阶段失败 |
| `enlist()` | 宿主已显式开启事务 | 仅宿主可以提交或回滚外层事务 | 本次写入尚待宿主提交，`committed()` 始终为 false |

两者要求 64 位 PHP、异常模式的 SQLite／MySQL PDO、1—30000 毫秒预算；MySQL 使用原生预处理并保持 `autocommit=1`。`enlist()` 可以加入原生 PDO 或 SQL 手工开启的事务，也可以从幂等执行器等组件的业务回调加入同一连接上的事务。不得在 `AtomicStore` 的可重试回调里调用业务 SQL 或外部服务。

构造只检查依赖和参数，不执行 SQL、不创建结构、不改写连接配置。组件只验证自身表结构；业务表的事务引擎、唯一约束、权限和数据生命周期由宿主负责。

## 识别实际事务

不以 `PDO::inTransaction()` 单独证明事务归属。旧版 PDO 可能漏报 SQL 手工事务，也可能在 SQL `COMMIT` 后保留旧标志。

SQLite 加入前尝试 `BEGIN DEFERRED`：只有数据库返回精确的“已有事务”错误才能加入；若空探测成功，则仅回滚这个由组件新建的空探测并拒绝调用，业务与权限回调均不执行。MySQL 核对实际 `autocommit`，再用随机保存点是否存在验证事务；`autocommit=0` 下保存点本身不足以证明此前已有宿主事务，因此显式拒绝该模式，不替使用方切换设置。

参考 [SQLite 保存点语义](https://www.sqlite.org/lang_savepoint.html)、[MySQL 保存点语义](https://dev.mysql.com/doc/refman/8.4/en/savepoint.html)及 [PDO 事务状态接口](https://www.php.net/manual/en/pdo.intransaction.php)。实际兼容性以本仓库运行记录为准，文档描述不能替代实际数据库检查。

## 局部回滚与归属丢失

加入后建立两个不同的随机保存点：固定的局部回滚边界，以及每次受控回调后重新确认的事务见证点。见证点刷新不能移动局部回滚边界，否则较早的入队写入可能在后续失败时残留。

权限回调严格返回 true 才执行主体；拒绝和已知失败会回滚本次局部写入，保留宿主此前的待提交写入及更早保存点。成功时明确释放两个保存点，不执行外层 `COMMIT` 或 `ROLLBACK`；MySQL 释放较早保存点不会自动释放较晚保存点，不能照搬 SQLite 的释放行为。

回调和自定义时钟必须遵守只读或同事务业务契约：禁止自行提交、回滚、重启事务、管理保存点、执行 DDL、切换连接状态或在数据库事务中发送网络请求。检测到事务结束／替换、保存点丢失或清理结果不确定后，实例拒绝复用，返回 `sql.cleanup`。组件不会回滚后来建立的宿主事务，也无法撤销错误回调已经提交的副作用。宿主必须中止当前业务流程、核对持久结果并重建连接，不能自动执行第二遍业务。

`enlist()` 失败后，**宿主必须中止整个业务单元**；保存点只防止局部残留，不能替调用方阻止任意后续 SQL。若宿主吞掉入队错误并提交业务，会造成“业务成功但消息缺失”。若保存点已释放，随后超时或恢复连接设置失败，局部写入仍可能待提交；同样必须由宿主回滚并核对，不能将错误解释为业务已经完整回滚。

超期处置的宿主审计与reconcile也遵循这一边界：在同一实际事务引擎／PDO记录已验证的决定，由当前决策guard读取并复核，再由宿主提交。局部失败不会撤销更早的待提交审计，因此发生错误后必须回滚整个宿主单元，避免只留下与实际处置不一致的审计。reconcile返回true及其commit阶段回调均不是宿主最终COMMIT成功证明。

## 时间预算与恢复

失败SQL语句显式关闭游标，避免异常栈保留的活动语句阻断保存点释放；关闭失败则报告清理不确定并禁止复用实例。操作前后检查实际耗时与注入时钟的单调性。临时收紧并恢复 SQLite `busy_timeout`／MySQL `innodb_lock_wait_timeout`，不切换自动提交和隔离级别；清理已知局部边界不依赖已经失效的时钟。支持传入同一个内部 `Deadline` 以共享剩余预算，不自动刷新预算或重试回调。

回调和阻塞驱动不能被 PHP 强制抢占；MySQL 锁等待的最小单位为秒，超过应用预算返回后会拒绝成功并尝试局部清理。宿主另需配置连接、网络及语句超时。死锁或数据库配置可能直接结束整个宿主事务，保存点也会丢失；此时报告清理不确定，不声称保留了宿主待提交数据。

出站消息必须和业务写入同库、同连接、同事务；发送端应在独立已提交的领取事务之后联网。业务提交确认丢失时，用新连接查询稳定业务执行记录与消息意图，不能根据 HTTP 响应或异常自动重做。外部接收成功但确认丢失仍可能重新投递，必须使用稳定投递编号和接收方唯一账本去重；完整 Outbox 实现和端到端验证继续 R4.3。

## 私有安全表的依赖边界

SDK 的显式 DDL 不声明外键。部署后的私有安全表也不能成为外键的引用端或被引用端：清理队列、幂等记录、接收历史或过期状态时，级联删除／更新会将影响扩大到宿主业务；只验证列、索引或启用状态无法排除这种副作用。

Outbox、幂等、Webhook 接收／处理在结构核对中查询两种方向的外键声明。即使当前连接关闭了外键执行也拒绝，不临时切换执行开关、不自动移除关系或改表。`MySqlStore` 在构造时验证，并在每次由它拥有的事务开始后重新验证，复用实例也能发现随后添加的关系；发现关系时不执行业务回调或删除。无关业务表之间的外键保持可用。

SQLite 明确查询 `main` 的结构和外键声明，并指定被检查的模式，TEMP 同名对象不能遮蔽查询；持久同名对象会导致拒绝。MySQL 按当前数据库及服务器的标识符大小写模式匹配，查询当前账号可见的出站及入站关系，包括可见的跨数据库引用；[官方 INFORMATION_SCHEMA 搜索规则](https://dev.mysql.com/doc/refman/8.0/en/charset-collation-information-schema.html)说明这些名称的比较会受文件系统和 `lower_case_table_names` 影响。

这一检查不是全部数据库的管理员审计：账号看不到的其他模式关系无法由查询证明不存在。宿主部署者仍需用具备相应可见性的账号核对完整 DDL，在变更前停止相关工作进程并执行互斥迁移，避免检查期间引入新关系。业务表应通过自身稳定业务键关联，不应依赖安全账本的保留期。结构不符合契约时先中止业务单元，由维护者审阅迁移，不能通过关闭外键检查绕过拒绝。

`tests/sql-schema-dependencies.php` 使用真实规范 DDL 追加依赖，覆盖双向外键、执行开关、组件拥有／宿主拥有事务、真实子记录保留、移除关系后正常清理以及已构造的存储实例。这里的私有数据库证据不能替代宿主线上 DDL 和迁移验收。

## 验证

`tests/sql-enlistment.php` 使用私有真实 SQLite／MySQL、独立观察连接和明确故障注入，检查提交前不可见、宿主提交／回滚、局部失败、早期宿主保存点、事务替换、超时、真实锁等待及连接清理；另与公开 `Idempotency\SqlExecutor` 组合，检查重放不再次入队、提交前撤权完整回滚、丢失提交确认后的独立连接恢复。

运行 `php72 tests/sql-enlistment.php`；私有无 TCP MySQL 使用 `python3 tests/mysql_check.py --sql-enlistment php72`。完整门禁已接入两后端，实际结果及未执行范围见 [verification.md](verification.md)。测试中的 intent 表是验证事务基础的测试数据，不能当作已交付的 Outbox 表结构。

短期限安全用例把测试预设准备与被测操作分离：预设先由真实初始化器在独立预算内建立，仅为空的私有测试根写入目标策略封存，再运行原250ms操作／350ms故障延迟。该逻辑位于被发行包排除的测试代码中，不是生产策略迁移接口，也不放宽被测操作期限。

## 同类实现参考与后续验收

[AWS 的事务发件箱模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)区分同库提交与独立发送，并要求处理重复和顺序问题；因此本包不能把“业务提交后调用发送函数”当作持久消息意图。

[Symfony Messenger 的幂等处理指南](https://symfony.com/doc/current/messenger.html#writing-idempotent-handlers)要求从稳定业务事件派生去重键并用数据库唯一约束保护；重新投递时生成新的随机编号不能承担这一职责。[Debezium Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html#basic-outbox-table)分别使用消息编号去重、聚合键维持分区顺序，这两种身份不能混用。

这些资料用于独立实现的契约对照，不引入对应框架或消息基础设施依赖。后续须实际验证稳定业务／投递编号、同聚合顺序、领取超时与旧确认、失败退避／死信／人工恢复、确认丢失后的重复投递，以及接收方在并发与重启后的去重；上述能力当前仍待实现。
