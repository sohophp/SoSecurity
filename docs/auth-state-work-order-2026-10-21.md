## 存储与持久权威契约

1. **完整来源**：SQL 覆盖实际账号凭据、角色／启用／MFA／地址字段、目录、恢复意图、审计及启用的通知／队列；声明完整字段、实际主键、筛选与容量。文件来源包括会话／挑战／因子／一次性授权的真实原始字节，不能忽略过期但尚未删除的记录。遗漏任何正在使用的存储或字段必须配置失败。
2. **实际服务绑定**：同一个 PDO、准确来源对象、覆盖指纹、真实会话 idle／absolute／时钟、因子目录策略、密钥环和 FileStore 命名空间必须相符。当前 `FileStateSnapshot::coversStore()` 只具体支持 FileStore 及有限 namespace 包装；不能把这个事实推广为 Redis／MySqlStore／任意 AtomicStore 已有完整见证来源。其他后端需显式实现和验收，之前受保护配置拒绝使用，不影响基础组件原有可选性。
3. **物理域隔离**：独立见证及独立审批的状态不随业务 SQL／会话／因子备份恢复。用当前 `StateStorageDomain` 的同目录／inode／数据库身份检查排除明显重叠，另由部署证明备份权限和恢复流程独立；代码中的 disjoint 不能证明运维不会同时回滚。多租户共用整个目录时，不允许不同独立见证相互修改对方摘要，必须使用经验证的共同物理域治理或真实隔离目录。
4. **互斥和身份**：最外层操作先取得独立权威的排他锁并检查稳定目录／inode／签名／代际／覆盖，再读取完整状态。进程、子进程和 Fiber 的上下文不得借用持锁能力。原 `LocalEpochFence` 的 SH／closed-EX 仍有自己的职责，统一锁顺序为独立见证→工作进程栅栏→SQL→物理存储；所有组合的真实调用链必须验证，不在 AtomicStore 重试回调内取外部锁或执行 I/O。
5. **先持久意图**：任何受保护状态／外部效果开始前，先确认 pending 记录的稳定持久化；记录绑定站点／scope／安全代际、来源指纹、修订、操作编号、准确动作／操作者／目标摘要、权限策略摘要和前序摘要，不保存密码、令牌或恢复码正文。
6. **真实耐久性**：只 `fflush` 或回调返回 true 不足以证明掉电持久化。PHP 7.2 的部署必须显式提供并验证能同步准确文件及必要目录元数据的持久化适配；缺失时拒绝启用保护模式，不引入基础密码／CSRF 功能的强制运行依赖。POSIX 文件语义、私有权限、锁、单链接及替换检测单列验收，不宣称网络文件系统／多节点一致性。
7. **成功完成**：受保护业务及其事务结束、最终权限／预算／时钟及新完整摘要核对成功后，才把相同操作完成为 current 并确认耐久性。嵌套组件不得提前提交检查点；宿主事务未完成不能报告最终成功，更不能替宿主隐式提交。
8. **有限格式及资源**：采用显式版本化签名域，当前原型格式 1／2 为 4 KiB、格式 3 为 16 KiB，仅是历史实现约束，SDK 新格式需单独冻结且旧读者拒绝未知格式。保留每份 FileStore 状态 64 KiB 等数据契约；不得用提高内存上限掩盖读取前限量缺失。完整恢复图历史已有 8 MiB 失败及 16 MiB 成功，不再笼统承诺整个恢复流程支持 8 MiB。

## 权限、拒绝与未知结果

公开请求的格式、scope、CSRF／来源策略和独立预算在受保护状态读取前验证；这些回调不能替代当前账号／对象权限。取得见证锁后，用同次 SQL／文件采集及固定无副作用评估器读取真实账号、会话、因子、封存账本、角色和期限，不通过任意身份回调读取“第二份当前状态”。评估失败不写 pending、不提升见证版本、不调用业务；下一次合法操作仍可继续。

错误证明导致尝试计数等预期安全副作用，与纯权限拒绝分别处理：前者只能在明确操作契约下进入 pending，受控完成并保存新 current 后返回业务拒绝；不能把“业务返回 false”自动当作未知，也不能把“SQL 已回滚”自动当作物理效果已撤回。执行阶段抛错或持久回执不确定则按未知结果处理。

| 权威状态／事件 | 允许的动作 | 禁止的动作 |
| --- | --- | --- |
| current，摘要和配置一致 | 完成只读权限复核后开始准确新操作 | 在不持有准确锁的情况下直接访问受保护存储 |
| 缺失、损坏、旧备份摘要不匹配、覆盖或代际不同 | 有界诊断和独立受控处置 | 自动 initialize、替换路径、采用当前数据库、跳过异常来源 |
| pending，或最终写入可能已完成但回执未知 | 检查准确操作号和原始回执；保持隔离 | 按异常自动重放业务、清 pending、改为旧 current |
| 独立批准后的 closed | 读取有界回执，按准确计划继续关闭态清理 | 恢复普通认证／修改，重新开放旧权威 |
| 新代际 quarantined | 精确处置账号／因子／授权／通知，独立批准续办 | 把当前可读状态当作可信新基线或授予普通登录 |
| 安全恢复提交 | 只有全部旧权限效果已处置、来源与审批仍匹配、恢复审计耐久后才能显式转换 | 在某一物理效果仍未知或外部投递尚待对账时宣称全部恢复 |

恢复管理员必须来自独立、不会随业务备份回滚的真实身份／会话／因子来源，具备指定管理角色、近期强认证、准备后的重新认证及一次性参数绑定授权。每次批准绑定准确未决根完整摘要、原动作／目标、当前审阅状态、来源指纹、安全代际、用途、期限和本次尝试号。普通会话、旧批准、不同动作／目标或单个布尔“允许”回调均不能解除隔离。

先永久关闭旧权威，再进入经审批的新隔离代际；保留原可信摘要、未知操作、批准回执和准确物理处置清单。物理清理只允许原始字节或已经确认的预期空封存，以 CAS、稳定条带锁及目录／句柄检查约束；部分成功后必须新审阅和新批准续办，不重新解释已经保存的清单。未经明确的数据丢弃授权，不批量删除业务账号或无关队列。

新代际最终恢复还必须使旧密码／会话／恢复码／API 凭据／待处理一次性授权及旧工作进程无法复活；具体启用能力必须逐类给出保留、重建、撤销或人工对账的安全效果，不能用一次清空会话代替全部状态处理。当前原型只有若干隔离处置阶段，尚无可以直接复用的完整安全恢复提交。

## 原型整合规则

当前原型差异清单仅用于审阅，不执行整目录覆盖。逐个比对 23 份缺失类型、17 份差异源码与主 SDK 后续改动，确认类型分类／接口兼容和共同依赖；共用格式纯校验可优先提取，但不能在只读权限判断里引入存储写入。移除对历史路径、任意允许回调、测试专用源和不真实持久化函数的依赖。没有主 SDK 全入口与恢复闭环证据前，不将 prototype acceptance.json 当作 G1—G6 的通过证据。
