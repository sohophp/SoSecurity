# Persistent upload quarantine

`Upload\Quarantine` combines an explicitly supplied `AtomicStore` with an existing private local spool. It does not start workers, create directories, initialize sessions or take over host authorization. The existing synchronous `Saver` API remains unchanged. See the [inert builder](../examples/upload-quarantine.php) and [scanner guide](upload-scanning.en.md).

After host authentication, object authorization, CSRF and quotas, call `enqueueUpload()` or use a trusted server-side path with `enqueueFile()`. Store the returned ID in the host resource record. A trusted bounded worker calls `process()` for one due job, or `process($id)`. Before every download, check current host permissions and call `readAvailable($id)`; it returns a digest-checked immutable `Candidate`, never a spool path. Descriptive status is not an access capability, and bytes already returned cannot be recalled.

The optional factory accepts an independent `upload_quarantine` configuration with required `directory`, `document_root` and `scanner` service name, optional fixed `scope` (default `uploads`), and nested `policy` and `queue` maps. Call `Security::quarantine()`. Existing `upload`/`uploader()` configuration remains independent. Scanning cannot be disabled; explicit `policy.require_scan=false` is rejected. Shared storage must be file, Redis, MySQL or an audited persistent custom AtomicStore; known memory/session stores are rejected. Native file-driver metadata must also be outside the configured web root. The host must protect opaque custom storage.

Configuration validation performs no filesystem/service initialization. Calling the factory validates services and existing directories without scanning or reading/writing jobs. Site and scope derive independent logical namespaces, including when sharing one physical store. Factory and direct-constructor scopes differ; drain and explicitly migrate before switching. Diagnostics inspect paths without invoking the scanner or reading tasks. Scanner, persistence and workflow remain manual checks; private paths and raw exception messages are not reported. Supplying an invalid or mismatched actual web root fails; omitting it leaves that check manual.

The lifecycle is staging → pending → scanning → available/rejected/retry/failed. Expired jobs are unavailable. A reservation commits before its exact random file is written with exclusive creation and 0600 permissions. The spool must be a canonical 0700 directory outside the web root. A permanent `.quarantine.lock` serializes staging writes and deletion across processes, with a one-second lock wait. Never remove the lock file while workers can use the spool. All ancestors and service accounts remain host responsibilities.

Scanning and filesystem operations run outside retryable atomic callbacks. Claims bind an attempt token and generation. Administrator rejection, rescanning or a newer claim invalidates old results. Content is checked before and after a clean scan and again when read. Only current available records can return bytes. A dead worker can be replaced after lease expiry, consuming another attempt. Adapter failures are retried within fixed limits; malformed content fails closed. The scanner must enforce its own transport deadlines; the workflow checks elapsed time before and after the call but cannot forcibly interrupt a third-party PHP adapter that never returns.

Defaults are 64 entries, 64MiB total reserved content, three attempts, a 60-second lease, a 30000ms scan budget, a 60-second retry delay and a fixed one-day lifetime. Allowed ranges are 1–64 entries, 1 byte–1GiB total, 1–10 attempts, 2–300 lease seconds, 1–30000 scan milliseconds, 1–86400 retry seconds and 60–2592000 lifetime seconds. The scan budget must fit inside the lease. Existing upload policy still limits individual bytes, types, pixels and memory. Terminal and staging jobs consume capacity until explicitly removed. Bodies are not stored in JSON; the existing 64KiB state codec remains a hard limit.

Host-authorized CSRF-protected administrative POST actions may call `rescan()` or `reject()`. Rescanning increases the generation and resets that round's attempts without extending lifetime. There is no manual “mark clean” operation. `remove()` accepts staging, rejected, failed, deleting or expired jobs: commit deleting, remove the exact file, then remove the record. Lost confirmation or cleanup failure retains an unavailable record for explicit inspection and retry. `items(1..64)` enumerates the bounded ledger, not the filesystem.

Files and arbitrary metadata backends are not one physical transaction. Crashes can retain unavailable staging/deleting jobs. PHP 7.2 uses fflush; platforms with fsync also flush content. This does not promise atomic power-loss durability. All workers need the same current authoritative metadata and protected local spool. NFS lock semantics, storage eviction, restores, global disk quotas and protection against privileged backup rollback require host controls. Scope is fixed by trusted server configuration. Directory identity and policies are bound; changing policy requires draining and an explicit migration.

Local tests use owned FileStore directories and PHP processes only. Core checks run at 8MiB; the separate `images` profile uses 32MiB to satisfy existing image-validation budgets and verifies real binary PNG/NUL contents. Process tests cover paused clean scans versus administrator rejection, actual SIGKILL lease recovery and staging/deletion exclusion. The [native HTTP/TLS/browser composition](upload-quarantine-native.en.md) has completed local stage checks; additional real metadata backends and full R4.4 acceptance remain open; production, remote CI and independent review have not been performed. See the [verification record](verification.md).
