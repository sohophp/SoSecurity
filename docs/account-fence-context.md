# 本地权威的执行上下文与锁清理

本次修复已写入主SDK的 `Account\LocalEpochFence`，保持公开接口、签名上下文、文件名和open／closed封存格式不变，没有表结构迁移。状态见证组合候选另同步相同修复，并禁止克隆 `StateBoundary`；它尚未整体接入SDK。

## 已确认的问题

此前工作及已关闭清理的借用只检查对象中的布尔标记或文件句柄。子进程继承对象后，即使父进程已经结束回调并永久关闭权威，仍可调用work／closedWork写入本地测试数据库；无关Fiber也可借用另一个挂起Fiber的活动上下文。活动对象克隆则会保留工作标记，原回调结束后仍能借用旧权威。

另一个准确反例中，子进程从继承的外层回调返回后执行LOCK_UN，提前释放了父进程仍在使用的SH锁。另一个排空操作随即取得EX锁并实际写入测试SQL，父工作回调却尚未结束。这是共享打开文件描述导致的锁生命周期问题，不能只增加工作入口的PID检查。

## 修复后的行为

持锁、工作与关闭清理分别记录进程及当前原生Fiber；跨上下文借用以factor.fence_context拒绝。嵌套工作还必须持有有效的原始句柄，并重新核对命名文件、inode和open状态。相同上下文中的正常嵌套继续支持，克隆的过期工作标记不能替代已经关闭的句柄。

清理只在最初取得锁的执行上下文中显式解锁；派生子进程只关闭自己继承的描述，避免替父进程解锁。回调异常或Fiber销毁时仍释放本地资源并清除活动标记；已永久关闭的状态保持关闭，不能用取消协程重新打开。

原有授权、范围／代际绑定、实际SQL审计和未知结果约束保持。此修复不替代全部宿主写入入口的约束，也不能阻止宿主在回调内绕过SDK直接调用PDO；所有写入者仍须遵守同一受控入口。仅替换源码不会改变已加载旧代码的常驻进程，正式升级须排空并重载相关工作进程；本次没有对在途或生产进程执行该操作。
