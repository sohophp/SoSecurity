# SoSecurity

## Local 1.0.0 delivery — not publicly released

The stable commitment covers **only S methods, ordinary configurations and accepted deployment conditions** in the [scope register](docs/stable-v1-api-scope.md). E entries remain experimental; historical management timeouts, unknown outcomes and SqlInbox failures are retained and unresolved. Do not configure or expose E entries, share protected directories/connections/processes, or downgrade existing authentication/MFA. PHP 7.2 retains fail-closed wall-clock rollback availability limits.

Start with the [PHP integration, dependencies and migration/rollback guide](docs/stable-v1-integration.md). [Acceptance evidence](docs/stable-v1-acceptance.md) binds the nine-runtime G/B/F/H/C gates and bounded Q checks to source fedc471. The external `delivery-manifest.json` and `SHA256SUMS` bind the final commit and ZIP; historical capability descriptions below are not a stable-method allowlist. No push, tag, registry publication or production deployment is authorized.

The optional [native quarantine composition](docs/upload-quarantine-native.en.md) supplies protected pages and a CLI worker with a host-owned SQLite example index; the SDK does not require that schema or provision default accounts.

Persistent upload quarantine now supplies private pending jobs, bounded retries, administrative rescanning/rejection and current-generation content snapshots. See the [guide](docs/upload-quarantine.en.md); full integration acceptance remains open.

Uploads can use a local ClamAV adapter with a shared total deadline, exact binary transfer and strict replies before private saving. See the [scanning guide](docs/upload-scanning.en.md).

Optional [read-only ZIP inspection](docs/archive-inspection.en.md) bounds paths, links, entry count, expanded bytes, and nested archives in a host-staged private file. It requires `ext-zip` and never extracts entries.

Bounded SQL, file and composite read-only snapshots are now available as standalone SDK APIs. They provide complete-byte digests and same-scan data, not authorization or independent freshness; see the [guide](docs/state-snapshots.en.md).

The opt-in [transactional Outbox core](docs/outbox.md) enlists durable intents in the host's existing PDO transaction, then uses separate committed claims and acknowledgements. Stable business-event and delivery IDs, aggregate ordering, bounded retries and maintenance, SQL field-read limits, an explicit factory and non-executing diagnostics are implemented. The [native adapters](docs/outbox-native.md) add CLI production and dispatch, constrained HTTPS delivery, signed reception and an independent transactional receiver ledger. [Receiver recovery](docs/outbox-recovery.md) uses a separate durable checkpoint and an external deployment epoch, refusing business history inconsistent with that checkpoint and permitting controlled recovery of only the last sealed transition. Epoch rotation requires an independently retained root hash. The [reconciliation core](docs/outbox-reconciliation.md) binds an expired intent to a received or durably cancelled decision inside the host audit transaction; this explicitly advances the namespace seal format to 2, which older workers reject. Native signed evidence, persistent cancellation fences, sealed audit retention and an optional independent authority store are implemented with local focused coverage. Full R4.3 acceptance remains open; configuring the core does not install schemas, initialize queues or send requests.

Private SQL security tables now reject incoming and outgoing foreign keys, even when foreign-key enforcement is disabled. This covers Outbox, idempotency, webhook intake/processing and MySqlStore; reused MySqlStore instances check again inside each owned transaction. Canonical DDL and public signatures are unchanged. Existing noncanonical relationships need an explicit reviewed migration; the library never removes constraints or changes enforcement settings. MySQL can inspect only metadata visible to its account, so host DDL review and migration exclusion remain required. See the [dependency contract](docs/sql-transactions.md#私有安全表的依赖边界) and [verification scope](docs/verification.md).

General SQL idempotency commits business writes and cached results on the same PDO, rechecks current authority, rejects parameter conflicts and retains expired key tombstones. Root format2 authenticates the ordered key/execution set; bounded maintenance compacts payloads and rotates seals. The [native Bearer example](examples/idempotency.php) adds current SQL account/version and object authorization, private CLI management, a mobile form and an independent business uniqueness ledger. It requires a trusted duplicate-rejecting ingress and never creates accounts or tables from HTTP. The latest nine-runtime focused integration passed SQLite409/MySQL356 assertions, HTTP433/TLS433, API contracts and fresh consumers; PHP7.2/8.5 TLS mobile Chromium passed as well. Full R4.3 acceptance remains open. See [core boundaries](docs/idempotency.md) and [native setup](docs/idempotency-native.md).

Opt-in webhook processing adds a lazy worker-only factory, non-executing diagnostics, a bounded standalone CLI and strong administrator retry forms. The shared SQLite host adapter commits a stable event ledger, business projection and processing success in one transaction. Known handler rollback can schedule bounded retries; uncertain commit or cleanup never automatically reruns the handler. Historical Ed25519 receipts can be processed without sodium or online publisher keys, using independent receipt seals and current business authority. PHP7.2/8.5 native TLS, mobile Chromium and fresh-consumer checks have passed for this integration stage; full R4.3 acceptance remains open. See [processing and recovery](docs/webhook-processing.md).

Webhook intake supports fixed Standard HMAC/Ed25519, Stripe v1 and GitHub SHA256 profiles, current endpoint keys, host association checks and explicit SQLite/MySQL durable receipts with independent integrity seals. Receiving a message does not execute its business effect. The [native example](examples/webhooks.php) separates signed deliveries from recent password/TOTP administrator access to bounded metadata. Its trusted ingress must reject duplicate headers before a SAPI can erase them; the example refuses deliveries without a server-owned validated-boundary attribute. Nine-runtime focused SQL checks and PHP7.2/8.5 native HTTP/TLS/mobile browser checks have passed; the complete nine-runtime gate, existing full-disk checks and fresh consumers have passed (PHP8.5 repeated serially after a default file-lock timeout under concurrent matrix load). These are R4.2 baseline results. A subsequently confirmed old-PDO SQL-transaction ownership issue in receive, processing and MySqlStore has been fixed and has passed a new 379-file nine-runtime complete/full-disk/fresh-consumer baseline, with PHP8.2 repeated alone after an external calibration wall-clock assertion under concurrent load. The later 388-file factory/native integration has passed its own focused nine-runtime checks; these are not a complete 388-file whole-library matrix. See the [guide](docs/webhooks.md).

Account-bound API credentials have passed R4.1 local acceptance. The opt-in registry requires live management sessions, explicit cross-account authorization and recent strong authentication for delegated issuance. Signed claims bind scopes, deadlines, policy and creator/issuer references; atomic generations support rotation, replacement and revocation. The native page uses actual password/TOTP authentication and separates Cookie management from Bearer-only, owner-scoped SQL reads/writes. Nine-version complete checks, full-disk recovery, fresh consumers, independent Python vectors, real-backend contention and native HTTP/TLS have passed, plus PHP7.2/8.5 TLS mobile Chromium. See the [guide](docs/api-credentials.md) and [native page](examples/api-credentials.php). Production integration remains separate.

Opt-in private downloads have passed R3.6 local acceptance. Trusted metadata binds the resource version, path, filename, byte count and full digest; current Session or signed-link authority precedes private-file I/O. Verified anonymous snapshots prevent reopening a substituted source, and each chunk rechecks current authority and metadata before returning bytes. The native page composes whole-source KiB budgets and explicit concurrency leases; it supports attachment responses, single ranges and explicit one-use POST redemption. Nine-version checks, fresh consumers, binary HTTP/TLS, low-memory and full-disk tests plus PHP7.2/8.5 Chromium passed. See the [guide](docs/downloads.md) and [native page](examples/authorized-download.php). Production and overall R1–R6 acceptance remain separate.

Opt-in signed links bind fixed origins, canonical URLs, the purpose, current resource/version, method and all query parameters. Retained shared ledgers support bounded lifetimes, optional caller binding, revocation and atomic one-use verification. The native example separates authenticated issuance from public reads and explicit CSRF-protected POST redemption. Nine-version local checks, independent vectors, shared-backend contention, fresh consumers and HTTP, plus PHP 7.2/8.5 Chromium, have passed. Production and native HTTPS success-path acceptance remain open; see the [guide](docs/signed-links.md) and [native page](examples/signed-links.php).

Opt-in operation authorization binds exact intents to fresh reauthentication, explicit confirmation and atomic one-use grants. The SQL example pairs unique execution receipts with resource/account versions and deadline checks; password records map effective identities to raw business versions and saved hashes. A standalone native page keeps secrets server-side and binds forms to the reviewed workflow. Nine-version local checks, shared-store contention, fresh consumers, real password/TOTP HTTP and PHP 7.2/8.5 Chromium have passed; production integration and the broader refinement remain open. See the [operation guide](docs/operations.md) and [native example](examples/operation-authorization.php).

Opt-in concurrency leases bind credentials to server-defined owners and resources, cap renewal lifetime, and retain fencing sequences in explicitly provisioned ledgers. Missing ledgers refuse acquisition. An exclusive SQL example pins epochs and checks fences, revisions and database deadlines; expiry does not stop a paused process or replace host-enforced write isolation. See the [lease guide](docs/leases.md) and [SQL integration](examples/leased-work.php).

Opt-in request budgets add integer-weighted token buckets, anchored fixed windows and exact second-resolution sliding histories. Single-owner groups debit atomically; ordered IP/account/tenant combinations retain earlier charges when a later dimension rejects. Shared-store failures, policy drift and reservations expiring during I/O refuse work. Existing rate limits and ban ladders remain compatible. See the [budget guide](docs/request-budgets.md) and [host example](examples/request-budgets.php).

Optional authorization adds default-deny policies, current-identity rechecks, explicit role/ownership/attribute constraints, field projection and complete batch preflight. The native SQL example scopes queries to the trusted tenant, fetches authorized columns and rolls back the entire host transaction on conflicts. Authentication remains the host's responsibility. See the [authorization guide](docs/authorization.md).

Password refinement matches byte limits to the hash profile, adds bounded local blocklists and optional HIBP prefix screening, limits verification work factors, and prevents automatic cost reduction. An explicit isolated CLI calibrator measures options without real-password inputs or configuration writes. See the [password guide](docs/passwords.md).

Optional persistent login adds explicit consent, fixed grant deadlines, atomic token rotation and replay revocation, device forgetting, and reauthentication for sensitive actions after restoration. It remains disabled until configured; see the [integration guide](docs/remembered-login.md).

Explicit authentication supports password/pending-MFA/full-session states, current identity and factor-version checks, per-session/all-session revocation, and reauthentication without extending absolute lifetime. Host CSRF, budgets and native Session rotation remain explicit. See [authentication integration](docs/authentication.md) and the [standalone example](examples/authentication.php).

The 2026-10-17 refinement adds optional encrypted TOTP enrollment, atomic replay protection, shared attempt budgets, single-use recovery codes, factor revocation, and key rotation. These require shared storage and `ext-sodium`; missing dependencies explicitly refuse operations. See the [MFA integration guide](docs/mfa.md) and [full R1–R6 tracking](docs/security-refinement.md). Authentication, authorization, CSRF, session revocation and lifecycle notifications remain explicit host responsibilities. The broader refinement is still in progress.

Framework-independent, modular PHP Web security helpers for **PHP 7.2–8.5**. Composer package: `sohophp/sosecurity`; namespace: `SoSecurity\`. Start with the [Chinese documentation index](docs/index.md).

The current version is a **local 1.0.0 delivery candidate, with only S usage stable and no public release**. Verify the fixed ZIP checksum in the external delivery manifest first. Use a Composer path repository with `"options":{"symlink":false,"versions":{"sohophp/sosecurity":"1.0.0"}}` and require `"sohophp/sosecurity":"1.0.0"`. Disable Packagist and install offline with `COMPOSER_DISABLE_NETWORK=1 composer install --no-plugins --no-scripts --no-interaction --no-progress`; do not ignore platform requirements. The complete local JSON is in the integration guide. The core requires PHP, JSON and hash, with no mandatory third-party runtime package.

Capabilities include CAPTCHA, stateful and signed stateless CSRF, application rate limiting and automatic/manual bans, passwords/reset tokens, opt-in session helpers, contextual output encoding, strict input validation, optional reviewed HTML cleanup, private uploads, HTTP/CORS/proxy/redirect policies, bounded pinned outbound HTTP, API credentials/HMAC/nonces, audit callbacks and diagnostics. Automatic bans reuse RateLimit; there is no system Fail2ban integration or separate AutoBan package.

Audit callbacks can use fixed-class counters and polled alert decisions backed by shared atomic storage. The host remains responsible for log persistence, alert delivery and deduplication; see the [audit guide](docs/audit-budget.md).

CAPTCHA includes digit/letter/mixed PNGs, addition/subtraction/multiplication/exact division, arithmetic images, server-verified slider and ordered click challenges, Turnstile, hCaptcha, and reCAPTCHA v2/v3. See the [CAPTCHA guide](docs/captcha.md); local challenges require rate limiting, and external business credentials are not preconfigured.

Components work independently. The optional `Security::fromArray()` factory validates configuration without starting sessions, sending headers, connecting services or creating directories. Eight [configuration presets](examples/configuration-presets.php) demonstrate common choices, including upload quarantine. Connections, private keys, a private upload directory and a scanner are explicitly supplied by the host. Shared sensitive state requires a suitable atomic backend; MemoryStore is test-only.

The [interactive local demo](http://72.rocky.wsl/SoSecurity/) covers normal, rejected and fault paths. Unconfigured external services are labelled accurately. Standalone [examples](examples) show gradual migration without replacing host authentication, routing, persistence or session ownership. Existing projects are only changed when explicitly requested.

All nine target PHP versions have local functional, fresh Composer consumer, isolated Redis/MySQL/HTTP and concurrency evidence. See [verification](docs/verification.md), [feature coverage](docs/features.md), [configuration](docs/configuration.md), [migration](docs/migration.md), [architecture](docs/architecture.md) and [contributing](CONTRIBUTING.md). CI configuration and author tests are not an independent audit or production acceptance.

Current work is limited to SoSecurity, standalone examples and the designated demo in the current environment. Previous Windows results are historical coverage; no further Windows setup is part of this plan. Private filesystem support and other boundaries remain explicit in [platform coverage](docs/platforms.md).

The library does not automatically cover business authorization entry points or define host permission rules, and does not replace parameterized SQL, HTTPS, runtime updates or infrastructure protection.
